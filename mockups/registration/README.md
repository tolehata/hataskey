# 登録申請と結果通知のモック

承認後の本番コードへの反映内容と検証結果は [IMPLEMENTATION.md](./IMPLEMENTATION.md) に記録しています。以下は独立したモックの説明です。

通常の **Hataskey UI（simple）** に合わせた、登録方法の選択、登録申請画面、拒否通知メールの操作モックです。`index.html` をブラウザで直接開けます。ビルド、追加パッケージ、プレビューサーバーは不要です。

実際の申請、審査、メール送信は行いません。入力はページ内だけで扱い、再読み込みで消えます。サーバー名・申請内容・宛先は架空のサンプルです。「サンプル入力」は入力例を埋めますが、文書リンクを開く操作や同意を代行しません。

## 確認する流れ

1. 最初の「招待コードをお持ちですか？」で登録方法を選びます。画面上部の「登録方法を選ぶ」からも開き直せます。
2. サーバールール→利用規約→プライバシーポリシー→個人情報の取り扱いを順に確認します。利用規約・ポリシーは設定されている場合だけ表示します。それぞれのリンクを別タブで開いて内容を確認し、戻ってから同意チェックを入れます。チェックすると次の項目が展開し、最後の同意で「次へ」ボタンが表示されます。「次へ」を押すと入力画面へ進みます。
3. 確認済みの項目は見出しから見直せます。同意を取り消すと後続の同意も解除します。入力から戻った際、同意済みなら「次へ」で戻れます。
4. コードを持っていない場合は登録申請です。申請理由、連絡先、ユーザーID、パスワード、メールアドレスを入力します。「管理者と関係がある」を選ぶと、理由の代わりに連絡先が必須になります。
5. コードを持っている場合は招待登録です。招待コードとアカウント情報を入力し、確認・完了のデモへ進みます。招待登録の内容は管理側の申請審査へ追加しません。
6. 内容確認から戻ると入力を維持します。パスワードは確認画面に出さず、受付完了時に入力欄から消去します。
7. 「審査・通知メール」で申請内容と通知文を確認し、「拒否して結果を通知」から最終確認へ進みます。ここは鯖缶による最終判断のプレビューです。通知失敗でも見送りを維持し、メールのみを再送する案を確認できます。
8. ライト／ダーク、PC／375px／320px、メールのHTML／テキストを切り替えて確認します。

## 利用規約・プライバシーポリシーの設定例

モックの設定欄で、利用規約とプライバシーポリシーをそれぞれ「設定あり（サンプル）」「未設定」「URLを指定」に切り替えます。初期値はサンプル設定です。サンプルは同じフォルダーの `terms.html` / `privacy-policy.html` にリンクし、正式な運用文書ではないことをページ内にも明記しています。

URL指定では入力後に「反映」します。HTTP(S)のリンクを表示し、相対URLは架空サーバー `https://example.com/` を基準に解決します。既知のサンプル文書だけがローカルファイルへの例外です。任意の `file:`、`javascript:`、`data:` URLや認証情報を含むURLはリンクにしません。空の設定は未設定として扱い、非空で無効な設定は表示エラーとして同意・先への進行を止めます。

リンクを開く操作をするまで、該当文書の同意チェックは無効です。リンクは別タブで開き、開くだけで同意や次への遷移は行いません。記録するのはリンクを開いた操作であり、他サイトの読み込み成功や読了を検証するものではありません。通常のクリック、Enterキー、中ボタンでのリンク操作を想定しています。右クリックメニューからの操作は記録できないため、ページ内のリンクを直接操作してください。

設定先が変わったら、その文書を開いた記録と同意を取り消します。入力途中の内容は保ち、必要な同意の確認へ戻ります。未設定の文書は順送りと必須判定から除きます。「個人情報の取り扱い」は申請・招待登録それぞれの情報利用の説明として残し、設定された正式なプライバシーポリシーとは別に扱います。

この設定欄はモック内の表示例を切り替えるもので、本番のサーバー設定を変更しません。外部文書の自動取得・埋め込みは行いません。指定した外部リンクを開くと、ブラウザからそのリンク先へアクセスします。

モックのルール・規約は表示確認用です。実運用の規約ではありません。ユーザーIDの空き、メールの利用可否、CAPTCHAはサーバーへ問い合わせません。招待コードは非空の入力だけを確認し、存在・使用済み・有効期限を照合しません。未入力・入力形式・パスワード確認など、ページ内で確認できる項目だけを検証します。本番の招待登録ではサーバー設定に応じたメール確認等の分岐がありますが、このモックでは完了表示の一例を示します。

## 今回の提案

- 入力前の説明、入力、最終確認、受付完了を分け、Hataskeyのパネル、ピル型ボタン、カプセルナビに揃えます。
- 英語の装飾的な補助見出しを取り除き、日本語の見出しと必要な説明に絞ります。
- 同意項目はチェックに連動して順に展開します。開閉、画面切り替え、モーダルの出入りは約260msの動きでつなぎ、OSの「視差効果を減らす」設定では即時切り替えます。
- 申請者には、承認・見送りの結果をメールで通知すると案内します。審査期限や再申請の可否は約束しません。
- 見送りメールは定型文にします。運営内の投票理由・判断メモ、SNS等の追加連絡先、パスワードは本文に含めません。
- 「拒否を確定できたか」と「通知を送信できたか」を分けて表示します。「通知済み（デモ）」はモックの状態であり、実配送の証拠ではありません。

このモックは本番Vue・API・翻訳・メールサービスを変更しません。`email-preview.js` は既存のメールレイアウトを参考にしたブラウザ用の独立したプレビューです。完成HTMLを本番の `sendEmail` にそのまま渡す設計ではありません。

`motion.js` は開閉と切り替えの共通処理です。操作の途中で次の要求が来た場合は前の動きを取り消し、古い完了処理が表示やフォーカスを巻き戻さないようにします。Web Animations APIが使えない環境では即時切り替えます。本番の規約画面には基本注意事項などもあるため、組み込む際にモックにある項目だけへ減らすものではありません。

### 本番化するときのデータと配送

現行の拒否APIはrevisionと審査権限を確認し、トランザクション内で拒否状態へ更新して、ユーザーID・パスワード情報・追加連絡先を削除します。メールと申請理由は保持されます。メールを含む拒否済み申請は、**申請日から90日経過後の定期削除まで**保管されます。

モックの通知には「申請したユーザーID」を載せるため、本番化では消去前の値が必要です。削除後にDBからIDを読み直す実装にはしません。通知にIDを載せない案も含め、配送に必要な情報だけを確保してください。審査がロールバックした場合に通知だけが出ないよう、状態確定後の配送を設計します。

再送ボタンはUI案です。現行の拒否APIには再送処理がありません。本番では配送状態、再送時の認可、重複送信の防止、配送キューに置く情報と保持期限を決める必要があります。SMTPが無効・未設定の場合を成功扱いにせず、審査失敗と配送失敗を分けます。配送サービスがメールを受け付けたことと、相手の受信箱へ届いたことも区別します。

## デザインとライセンス

配色は `packages/frontend-shared/themes/l-cherrypick.json5` / `d-cherrypick.json5`、形状は `simple.vue` と `MkButton.vue`、メールは既存 `mockups/email/` を参考にしています。Hataskey UI S・3ではなく、通常UIの候補です。

新規コードはリポジトリと同じ **AGPL-3.0-only**。既存のLINE Seed JPを相対パスで参照し、フォント自体は **SIL OFL 1.1**（`packages/frontend/assets/fonts/LINE-Seed-JP-OFL.txt`）のままです。新しい依存パッケージ・外部素材・CDNは追加していません。

## 検証

JavaScriptの構文検査、CSSの構文解析、HTMLの参照先とローカル素材の存在確認を実施しました。既存のHappy DOMで、同意エラー、条件付き必須項目、入力内容の保持、パスワードの長さ・確認不一致・受付後の消去、拒否のキャンセル、通知失敗・再送、処理中の二重操作防止、テーマ・表示幅・テキスト切り替え、リセットを検査しています。

メールは両テーマ、動的値のHTMLエスケープ、件名の改行拒否、運営内情報の非掲載を検査しました。これはブラウザの描画検査ではありません。

順送りへの更新後は、先の項目へのスキップ防止、同意解除による後続解除、招待コードの必須入力、モード別の説明、招待登録と審査データの分離もHappy DOMで検査しました。規約確認完了後の入力画面への遷移は「次へ」ボタンで行います。アニメーション有効時の連続チェック、開閉反転、遷移中リセット、登録方法の連続選択、終了時のスタイル復元を確認しています。別途、制御したアニメーションAPIで、取消済み処理の無効化、親の位置指定がない場合の測定、動きを減らす設定、モーダルが閉じ終わるまで表示を保持する動作を検査しました。

リンク確認への更新後は、未操作時の同意制限、クリック・中ボタン操作後の有効化、リンク操作だけでは同意・次への遷移を行わないことをHappy DOMで確認しました。設定の有無、相対URL、無効URL、同じURLの再反映、変更時の同意解除と入力保持、完了後の設定変更、サンプル入力で未確認の同意を省略できないことも検査しています。動きが有効な状態で設定変更・リセットを重ねた場合、招待登録の必須入力と審査データの分離、通知失敗からの再送も通過しました。新しいサンプル文書は参照先、フォント許可、ダークテーマの配色指定を静的に確認しています。

ブラウザでの目視と実メールクライアントでの受信確認は未実施です。本番への接続、実送信、DB操作、デプロイはこのモック作成に含みません。

「次へ」への変更後は、申請・招待登録と文書設定の有無を組み合わせて確認しました。最後の同意後に規約確認画面へ留まること、ボタン表示とフォーカス、明示的なクリックによる入力画面への遷移、同意取消・URL変更時の非表示をHappy DOMで検査し、アニメーション有効時にも通過しました。
