# 花常 イベント基盤 設計書

前提: **HANATSUNE-CONSTRAINTS.md を先に読むこと。** 本書はその制約の中でのみ成立する。
特に INV-1〜4(無償のみ・換金譲渡不可・寄付非連動・挙動同一)と §4.1A の壁 W-1〜W-6 は絶対条件。

## 1. 配信方式(⚠️バックエンド変更ゼロで管理者が設定できる仕組み)

### 1.1 なぜ静的JSONなのか
- `i/registry` は**ユーザーごと**の保存領域であり、管理者が全員向けの設定を配る用途に使えない
- バックエンドに設定用エンドポイントを足すと、パージ容易性が壊れる(CONSTRAINTS §2-5)
- `vite.config.ts:163` と `ClientServerService.ts:316-321` により、
  `packages/frontend/assets/` は `/client-assets/` で**静的配信済み**。追記不要で使える

→ **イベント定義は `assets/hanaawase/events/` 配下の静的JSON**とし、
実行時に `fetch` する(バンドルに含めない)。**ファイルを差し替えるだけで反映**され、再ビルド不要。

### 1.2 ⚠️7日キャッシュ問題(実コードで確認済み)
`ClientServerService.ts:319` が `maxAge: ms('7 days')` を設定しているため、
素朴に置くとファイルを差し替えても**最大7日間クライアントに反映されない**。対処:

| ファイル | 取得方法 | 理由 |
|---|---|---|
| ~~`events/index.json`~~ → ⚠️**API `games/hanaawase/event-index`** | ⚠️`fetch(url, { cache: 'no-store' })` は**そのまま維持**（§1.1-b） | 常に最新が必要(開催時間はここ)。⚠️**静的ファイルは廃止**したが、`no-store` を外してよい理由にはならない |
| `events/<id>/event.json` | `fetch(\`...event.json?rev=${rev}\`)` | `rev` は index.json 側が持つ。**URLが変わるのでキャッシュ7日で問題ない** |
| 画像・本文 | `?rev=` 付き | 同上 |

⚠️Codex: `index.json` だけは必ず `no-store`。ここを普通に fetch すると
「イベントを終了させたのに終わらない」という**最悪の事故**が起きる。

```ts
// ⚠️この形以外で index.json を取らない
await fetch('/client-assets/hanaawase/events/index.json', { cache: 'no-store' });
```
- 根拠: `ClientServerService.ts:319` が `maxAge: ms('7 days')`(= `max-age=604800`)を返す。
  ⚠️素で fetch すると**最大7日間、緊急終了が効かない端末が生まれる**
- SWは無関係(`sw.ts` はHTMLのみ横取り。確認済み)
- ⚠️`no-store` は **`index.json` だけ**。`event.json`・画像・本文まで `no-store` にすると
  毎回取り直しになって重い。あちらは `?rev=` でURLを変える

### 1.3 ディレクトリ構成
```
packages/frontend/assets/hanaawase/events/
  index.json                  ← イベント一覧・開催時間・rev(★管理者が触る唯一のファイル)
  <eventId>/
    event.json                ← イベント定義(ステージ・報酬・交換所・ギミック指定)
    home.json                 ← イベントホームの構成(§8)
    story/*.json              ← イベント本文
    progress.json             ← 集会の全体進捗(§9。任意・バッチ生成)
    img/                      ← ロゴ・キャラ・ホーム背景
```

### 1.4 取得できないときの挙動(⚠️必須。fail-closed)
`index.json` の取得に失敗したら、**イベント機能を静かに無効化**して本編は通常どおり遊べること。
⚠️エラーモーダルを出さない。イベントは本編の付加物であって、落ちたら本編ごと止まる設計にしない。

- ⚠️**前回取得した index を流用して「開催中」を続けない**(fail-closed)。
  fail-open にすると、**緊急終了が効かない端末が生まれる**。これは「終わらせたのに終わらない」のと同じ事故
- ⚠️失敗を「イベントが終わった」と**書かない**。イベントの入口ごと出さない(黙って消える)。
  ⚠️「読み込めませんでした」と赤字で出すのも違う。⚠️再試行ボタンを置かない(次に開いたときに取り直せばよい)
- 既に保存済みのポイント・交換済み・進行は**そのまま残す**(表示できないだけで、消さない)

### 1.5 再取得のタイミング(⚠️プレイ中は判定しない)
| いつ | 取り直す |
|---|---|
| ゲームのマウント時 | ○ |
| イベント画面へ入るたび | ○ |
| `visibilitychange` で visible になったとき | ○ |
| リザルト確定後 | ○ |
| ⚠️**1局のプレイ中** | ⚠️**× 判定しない** |

メモリキャッシュのTTLは **60秒**(同じ操作で連打しても取り直さない)。

⚠️**プレイ中に開催時間の判定をしない。** 緊急終了が走っても、
**遊んでいる1局は最後まで遊ばせ、報酬(ポイント)も通常どおり付与する**。
⚠️局の途中で盤面を閉じたりポイントを没収したりすると、利用者には「データが消えた」としか映らない。
判定は**次にイベント画面へ戻ったとき**に効かせれば十分早い。

## 2. `index.json` のスキーマ

```jsonc
{
  "v": 1,
  "events": [
    {
      "id": "irifune-yomise",          // 不変。復刻しても変えない
      "title": "入舟夜市",
      "rev": 3,                         // 中身を更新したら +1(キャッシュ破棄用)
      "runs": [                         // ★再びの開催はここに追加するだけ
        { "start": "2026-08-01T00:00+09:00", "end": "2026-08-18T00:00+09:00", "label": "初回" },
        { "start": "2027-08-01T00:00+09:00", "end": "2027-08-18T00:00+09:00", "label": "再びの開催" }
      ],
      "archiveFrom": "2026-08-18T00:00+09:00"  // これ以降アーカイブで読める(§7)。⚠️初回の end と同値
    }
  ]
}
```

- ⚠️**日時は必ずタイムゾーン付きで書く**(CONSTRAINTS §1「タイムゾーン明記」)。
  判定は §6 デイリーと同じく**JST固定**で行い、端末TZに依存させない
- **開催中の判定**: `runs` のいずれかが **`start <= now && now < end`** を満たせば開催中
- ⚠️同時開催を許す(複数イベントが `runs` で重なってよい)。UIは開催中のものを列挙する

### 2.1 ⚠️`end` は「終了日の**翌日** 0:00」を書く(半開区間)

⚠️**`"end": "2026-08-17T23:59+09:00"` と書いてはならない。**
判定を `now <= end` にすると **23:59:01〜23:59:59 の59秒が宙に浮き**、
`archiveFrom: "2026-08-18T00:00+09:00"` との間に「開催中でもアーカイブでもない」空白ができる。

| 決めごと | 内容 |
|---|---|
| 判定 | ⚠️**`start <= now && now < end`**(半開区間)で統一。`<=` を両端に使わない |
| `end` の値 | ⚠️**終了日の翌日 `00:00+09:00`**。「8月17日まで開催」なら `2026-08-18T00:00+09:00` |
| `archiveFrom` | ⚠️**最初の run の `end` と同値**にする。空白が消え、切れ目なくアーカイブへ移る。⚠️再びの開催を足しても動かさない |
| 画面表示 | 内部値は翌日0:00だが、⚠️**人に見せるときは「8月18日(火) 0:00 まで」**と書く(§2.5-A)。「17日23:59まで」と書き換えない |

⚠️**緊急終了で `end` に現在時刻を入れる場合だけは、翌日0:00の規則から外れてよい**(その瞬間に閉じるのが目的)。
⚠️**初回の run を緊急終了したときは `archiveFrom` も同じ値に揃える**(揃えないとアーカイブに現れるまで空白が生じる)。
2回目以降の run を緊急終了した場合は `archiveFrom` を動かさない(既に読めるようになっているため)。

## 2.5 開催時間の表記(⚠️UI文言の正本)

⚠️**表記のゆれは「別の期間があるのか」と読まれる。** 役割ごとに語を1つに固定する。
⚠️統一するのは**日本語表記だけ**。`runs`/`start`/`end`/`label` などの**JSONキー名は改名しない**
(管理者が触るスキーマを表記の都合で変えると、互換が切れる割に得るものがない)。
⚠️台詞タグ名(`序盤`/`中盤`/`終盤`)も**変えない**(`event.json` のデータに埋まっているため)。

### 2.5-0. 語の対応表
| 役割 | 採用語 | ⚠️使わない語 |
|---|---|---|
| 時間の範囲(見出し) | **開催時間** | 開催期間／会期／開催時期／期間 |
| 範囲内にある状態 | **開催中** | (据え置き。別概念なので潰さない) |
| 終わりまでの猶予 | **開催時間 のこり N日** | 残り期間／あと◯日(単独) |
| 開催前 | **開催時間 N月N日から** | 近日開催／まもなく |
| 終了後 | **開催時間 終了しました** | 終了間近／終了済み |
| 2回目以降 | **再びの開催** | 復刻(⚠️UIには出さない。**本書のような文書内の運用語としては残す**) |

⚠️「開催時間」は本来「営業時間」に近い含みを持つので、**必ずラベル＋値の形で出す**(値を省いて孤立させない)。

### 2.5-A. 完全表記(告知・イベントの扉)
```
開催時間
2026年8月1日(土) 0:00 から
2026年8月18日(火) 0:00 まで(日本標準時)
```
- ⚠️**タイムゾーンを画面に明記する**(CONSTRAINTS §1 の必須要件)。
  ⚠️表記は**日本語で「日本標準時」**。`JST` や `+09:00` と画面に書かない
- ⚠️端末TZに依存させない。§6 デイリーの `JST_OFFSET_MS` 方式を流用する

### 2.5-B. 一行表記(イベントホーム)
| 状態 | 文字列 |
|---|---|
| 開催前 | `開催時間 8月1日から` |
| のこり2日以上 | `開催時間 のこり 6日` |
| 同日中に終わる | `開催時間 本日まで` |
| 終了後 | `開催時間 終了しました` |

- ⚠️**「のこり 0日」を出さない。** 最終日は**「本日まで」**
- ⚠️残り日数は**JSTの日付境界で数える**。⚠️時刻差を `86400000` で割らない
  (割ると同じ「明日まで」が端末の時刻によって0日にも1日にもなる)
- 色は `--sub`。⚠️赤字・点滅・大きな数字にしない
- ⚠️**「お見逃しなく」「今だけ」「二度と手に入りません」を書かない**
  (再びの開催があるので焦らせる理由がない。最後のものは CONSTRAINTS §2-2 の明確な禁止)

### 2.5-C. アーカイブ
季節表記(「初夏」)を主に残す。⚠️一覧に日付を並べない。
扉を開いたときだけ 2.5-A を**「これまでの開催時間」**として出す。

### 2.5-D. `runs` が複数あるときの表示規則
1. 現在時刻が入っている run を「**開催時間**」として出す
2. 無ければ**未来で最も近い** run を「**開催時間 N月N日から**」
3. 未来も無ければ「**開催時間 終了しました**」

過去の run は**扉の中でだけ**列挙する。
⚠️`runs[].label` は**そのまま画面に出る**。したがって `index.json` に書く値を
**「初回」「再びの開催」**にする(⚠️コード側に変換の分岐を書かない。パージが重くなる)。

## 3. 開催時間の運用(管理者の作業)

イベントの開始・延長・緊急終了は、**`index.json` を書き換えるだけ**。再ビルド不要、再起動不要。

| やりたいこと | 操作 | ⚠️同時に直すもの |
|---|---|---|
| 開始日を変える | `runs[].start` を書き換える | 告知文の日付 |
| 延長する | `runs[].end` を後ろにずらす(⚠️新しい終了日の**翌日 0:00**) | `archiveFrom`／告知文 |
| 緊急終了 | `runs[].end` を**現在時刻**にする | ⚠️`archiveFrom` を**同じ値に**揃える |
| 再びの開催(復刻) | `runs` に要素を1つ足す(`label: "再びの開催"`) | — |
| 中身を直す | 該当ファイルを直し、`rev` を +1 | — |

- ⚠️`end` は**終了日の翌日 `00:00+09:00`**(§2.1)。⚠️`23:59` と書かない
- ⚠️`archiveFrom` は**最初の run の `end` と同値**にする。ずらすと「開催中でもアーカイブでもない」空白ができる。
  ⚠️再びの開催を足しても**`archiveFrom` は動かさない**(一度読めるようにしたものを読めなくしない)
- ⚠️書き換えたら**必ず1台で実物を確認する**。`index.json` を `no-store` で取っていない実装が混じっていると
  緊急終了が効かない(§1.2)。⚠️「置いたから終わったはず」で済ませない
- ⚠️`id` は**変えない**(再びの開催でも同じ `id`)。変えると利用者の交換済み・進行が別物になる

⚠️**開催中に報酬内容を減らす変更をしない**(CONSTRAINTS §2-2「事前予告なく減額・削除」の禁止)。
不具合対応は例外だが、その場合は変更履歴ページに記録すること。

⚠️緊急終了しても、**その瞬間に遊んでいる1局は最後まで遊べ、報酬も付与される**(§1.5)。
これは不具合ではなく決めごとなので、⚠️「終了後に報酬が入った」という報告を事故として扱わない。

## 5. イベント限定ギミック(拡張点の設計)

**データだけでは新しい遊びは作れない。** ギミックは**コード**だが、
**engine の外側に差し込む形**にして、イベントごとに増やしても engine が汚れないようにする。

```ts
// hanaawase/gimmicks/index.ts
export type Gimmick = {
  id: string;
  /** 盤面生成時に一度だけ呼ばれる */
  onInit?: (board: Board, params: any, rng: Rng) => void;
  /** 手番の解決後に呼ばれる。追加の消去やマス変化を返す */
  onResolve?: (board: Board, ev: ResolveEvent, params: any) => GimmickEffect[];
  /** 描画用の追加レイヤー(SVG/DOM)。無ければ null */
  render?: (board: Board, params: any) => VNode | null;
};
export const GIMMICKS: Record<string, Gimmick> = { lantern, ... };
```

- `event.json` の `gimmick.id` が `GIMMICKS` に**無い場合はギミック無しとして動く**(⚠️落とさない)
- ⚠️**engine.ts 本体に `if (eventId === ...)` を書かない。** 必ず GIMMICKS 経由
- ギミックは**本編ステージでは使わない**(本編のひねりは §3.4「季節外れの花」だけ、という方針を守る)

### 初回イベントのギミック例(軽いもの1つに留める)
`lantern`(提灯): 盤面に提灯マスが数個置かれ、隣接で消すと点灯する。全部点灯で追加スコア。
⚠️1本目から重いギミックを作らない。**基盤が正しく動くことの確認が目的**。

## 5.5 周回要素

### 位置づけ(⚠️トーンと衝突させないための整理)
「同じステージを何度も遊ぶ」はソシャゲの語彙だが、**本作では物語のテーマと一致する**。
本編8月「無心の手」で、若菜は仏花を三十束作り、**三十束目で頭が空になる**。
花屋の仕事は毎日同じことの反復であり、その反復の中で手が覚えていく——これが本作の主題のひとつ。

→ 周回は「**手を動かす**」として提示する。⚠️「周回」「周回数」という語をUIに出さない。
表示は「**通いの記録**」「今日の手」等、店の言葉で書く(SPEC §2.4 の漢語基調に従う)。

### 設計(⚠️ソシャゲの搾取的パターンを持ち込まない)
| 項目 | 決定 | 理由 |
|---|---|---|
| スタミナ・行動力 | ⚠️**作らない** | 無償でも「待たせて課金を促す」形式そのもの。CONSTRAINTS の方針に反する |
| 1日の回数制限 | ⚠️**作らない** | 遊びたい人を止めない |
| ポイントの逓減 | ⚠️**作らない** | 「周回するほど損」は不快なだけ。レートは**常に一定** |
| **総量の上限** | ⚠️**交換所を取り切ったら終わり**(下記) | 無限の作業を発生させない |
| 物語の周回ゲート | ⚠️**作らない** | ⚠️**周回しないと話が読めない設計にしない**。物語は初回クリアで全部読める |

### 「取り切ったら終わり」の設計(★最重要)
本作には無限の育成対象が無い。だから**周回に終わりを作る**。

- 交換所の全アイテムを取り切るのに必要な総ポイントを、**開催時間の中で無理なく到達できる量**にする
- 目安: **1周 2〜3分(手数15前後)** × **20〜30周**で全交換完了。
  2週間開催なら**1日2回弱**。⚠️「毎日張り付かないと取り切れない」量にしない
- 取り切ったあとも遊べるが、**それ以上ポイントは貯まらない**ことを明示する
  (⚠️貯めても使い道がないのに貯まり続けるのは不誠実)
- ⚠️**取り逃しても復刻がある**(§3)。だから焦らせる文言を書かない

### 周回のための快適さ(ここは手を抜かない)
- リザルトから**即再挑戦**(1タップ)。マップに戻らせない
- 2周目以降は**開始前モーダルを省略**できる(道具の持ち込みが前回と同じなら確認しない)
- 演出は**スキップ可能**(⚠️§9のjuiceは残しつつ、リザルト演出だけ短縮)
- 待機時のひとこと(§3.57)は周回中も出す。⚠️**同じ文が続かないよう、周回をまたいで既出を記憶する**

## 6. 報酬と交換所

⚠️**CONSTRAINTS §1「交換所(この形なら安全)」に厳密に従う。** 逸脱不可。

```
[イベントステージのクリア] → [イベントポイント(単一残高・無償のみ)] → [交換所でアイテム]
```

- ポイントは**イベントごとに独立**(`points.id`)。イベント終了で失効する場合は**取得時点で明示**
- 交換先は次の2種のみ:
  1. **道具**(鋏/手直し/打ち水。§3.55の在庫に加算。上限5は据え置き)
  2. **飾り**(`kazari-*`。⚠️**ゲーム内の見た目だけを変える**。性能に影響しない)
- ⚠️`limit` で交換回数の上限を設ける。**交換レートは開催中に変更しない**
- ⚠️**譲渡UIを作らない**(APIレベルでも)
- ⚠️**確率表示をしない。そもそもランダム性を交換所に入れない**(CONSTRAINTS §2-2)
- ⚠️**コンプリート型(N種そろえて交換)を作らない**(CONSTRAINTS §2-1、§4-4)

### 「飾り」というアイテム種を新設する理由
本作には通貨もガチャも無いので、報酬に出せるものが乏しい。
**性能に一切影響しない見た目のアイテム**なら、集める動機になり、かつ INV-2(換金・譲渡不可)と
「無償で全要素が遊べる」方針を一切損なわない。飾りの用途:
- 花手帖の見開きに飾る / イベントホームに飾る / 帳面の栞の意匠を変える

⚠️飾りは**本編の難易度・進行に一切影響しない**。ここを崩すと「持っている人が有利」になり、
方針(全員が同条件)と衝突する。

## 9. 集会(共通目標)— ⚠️正直な制約

**共通目標は「全員の合計値」を扱うため、本質的に共有状態が必要**。
`i/registry` はユーザーごとなので、これだけでは実現できない。

### 採る方式: バッチ集計 + 静的JSON(⚠️アプリのバックエンド変更ゼロ)
1. 各ユーザーの貢献値は**自分の registry に貯まる**(通常の保存)
2. 管理者が**運用スクリプト**を定期実行し、registry を集計して
   `events/<id>/progress.json` を書き出す(例: 1時間ごと)
3. クライアントは `progress.json` を `no-store` で取得し、全体進捗を表示

利点:
- バックエンドに**エンドポイントもテーブルも追加しない**。スクリプトは消せばなくなる
- リアルタイムでないことは、CONSTRAINTS §1 の**「非同期・共通目標」**という
  最も安全な集会形態と一致する

### 制約(⚠️正直に書く)
- **リアルタイムではない**(最大1時間の遅れ)。「今まさに増えている」演出はできない
- 集計スクリプトが動かなくても**イベントは成立する**(進捗が止まって見えるだけ)。
  ⚠️落ちたときに本編が止まらないこと
- ⚠️**貢献度の順位を出さない**(CONSTRAINTS §2-2「実質ランキング」の禁止)。
  出すのは**全体の合計としきい値到達**のみ
- 意思表示は**定型スタンプ/定型文の選択のみ**。⚠️フリーテキストを入れない

### v1での判断
⚠️**1本目のイベントでは集会を実装しない。** 基盤(配信・開催時間・報酬・交換所・アーカイブ)が
正しく動くことを先に確認する。集会は2本目以降に、上記の方式で追加する。

## 12. イベントで**やってはならない**こと(再掲・厳守)

## 13. 管理者の運用手順(⚠️backend実装を採らない前提の正本)

「管理者がプレイ状況を把握したい」を、**コードを1行も書かずに**満たすための手順。
⚠️**案D(backendにエンドポイントを足す)は採らない**(CONSTRAINTS §2-5「backendへの新エンドポイント」)。
採るのは **①運用SQL ＋ ②匿名集計 ＋ ③本人による書き出し** の組み合わせ。

| 手段 | backend変更 | パージ影響 | 個人別 | 使いどころ |
|---|---|---|---|---|
| **① 運用SQL** | ゼロ | なし | **可能** | 不具合の再現調査。⚠️必要が生じたときだけ |
| **② 匿名集計JSON** | ゼロ | なし | 不可 | ⚠️**日常はこれだけで足りる**(人気の面・詰まる面・離脱点) |
| **③ 本人が書き出す** | ゼロ | なし | 本人のみ | 問い合わせ対応。①を引く回数自体が減る |
| ⚠️案D backend実装 | エンドポイント＋SDK再生成＋マイグレーション | ⚠️**崩壊** | 可能 | ⚠️**採らない** |

### 13.0 ⚠️`iAmModerator` は認可ではない
⚠️`$i.iAmModerator` は**フロントの表示制御**であって、**サーバー側の認可ではない**。
これで隠しても、データがAPIから返るなら**非モデレータが直接APIを叩けば取れる**。
⚠️したがって「モデレータにだけ他人の記録を見せる画面」を**フロントだけで作らない**
(作るならサーバー側の認可が要る＝それが案Dの費用の本体)。

### 13.1 ① 運用SQL(個人別。⚠️必要が生じたときだけ)
花常の保存先は registry(`storage.ts` の scope `["client","hanaawase"]`)＝**`registry_item` に既に入っている**。
⚠️アプリのAPI経由では他人の分は取れない(`i/registry/get` は `me.id` 固定、`admin/` に registry 系は無い)が、
**DBを直接引けば読める**。

```sql
SELECT u.username, r.key, r.value, r."updatedAt"
FROM registry_item r JOIN "user" u ON u.id = r."userId"
WHERE r.scope = '{client,hanaawase}' AND r.domain IS NULL;
```

⚠️CONSTRAINTS が禁じているのは**backendへの新エンドポイント／エンティティ／マイグレーション**であって、
運営者が自分のDBを読むことではない。よって制約を1つも破らずに実施できる。

**引くときの決めごと(⚠️これを守れないなら引かない)**
- **目的を限定**: ⚠️**不具合の調査と難易度の調整のみ**。§3.59 の開示にそう書いた以上、それ以外に使わない
- **引ける人を限定**: ⚠️**DBに入れる人＝サーバー管理者**。モデレータ全員ではない
- **記録を残す**: ⚠️**誰が・いつ・何のために引いたか**を残す(統制の実体は「記録が残る」こと)
- ⚠️**結果を個人が識別できる形で公開・投稿しない**(スクリーンショットを含む)
- ⚠️`updatedAt` は**最終プレイ時刻に相当する**(CONSTRAINTS §2-3「最終ログイン時刻等の推知」に触れる)。
  **他者に見せない**
- ⚠️JOIN は `username` の解決までに留める。**フォロー関係・ロール・寄付状態を引かない**(W-2)

### 13.2 ② 匿名集計JSON(日常はこれ)
①と同じSQLの結果を**個人を落として**集計し、静的JSONとして置く(§9 の `progress.json` と同じ経路)。

- ⚠️**個人別データを静的JSONに置くのは絶対禁止**。
  `/client-assets/` は**URLを知れば誰でも読める**。この経路に載せてよいのは**匿名集計だけ**
- 匿名集計を誰でも読める場所に置くことは**許容する**(2026-07-26 利用者決定)
- ⚠️**1件しか該当しない粒度で出さない**(「そのステージを遊んだ人が1人」は事実上の個人特定)。
  ⚠️**人数の少ない区分はまとめる**
- 出してよい例: ステージごとのクリア率・平均手数余り・離脱の多い面・イベントの総プレイ数
- ⚠️出さない: ユーザー名・ID・最終プレイ時刻・順位・貢献度の個人値(CONSTRAINTS §2-2「実質ランキング」)
- ⚠️`progress.choices`(物語の分岐)は嗜好そのもので感度が高い。⚠️個人に紐づけて見ない。
  見るなら**匿名の比率のみ**

### 13.3 ③ 本人による書き出し
設定に「**記録を書き出す**」を置き、**自分の保存内容をそのまま**取り出せるようにする。
- 問い合わせのとき、⚠️管理者がDBを引かずに**本人に送ってもらえば済む**
- ⚠️これはゲーム内で完結する(registry を読んでファイルにするだけ)。backend変更ゼロ

### 13.4 集めない・作らないもの(⚠️既存の3キーで目的は足りる)
目的(①難易度調整 ②離脱点 ③不具合再現 ④イベントの手を動かした量)は**既存の保存だけで達成できる**。
- ⚠️**1手ごとの操作ログ・盤面ログ** — そもそも保存していない。⚠️**新設しない**
- ⚠️**花常の外の情報**(フォロー関係・ロール・寄付状態) — ⚠️**取得箇所自体を作らない**(INV-3/W-2)
- ⚠️**IP・UA・端末情報** — 一切扱わない
- ⚠️新しい保存フィールドを足すのは SPEC §14 の「要相談(保存スキーマ)」。⚠️勝手に足さない

### 13.5 開示との整合(⚠️これを書いた以上、守る)
§3.59 の注意書きに**データの扱いの3ブロック目**を置いてある(実装済み)。
```
遊んだ記録(進み具合・遊んだ回数・設定)は、このサーバーの
あなたのアカウントに保存されます。サーバーの管理者は、
不具合の調査と難易度の調整のためにこれを見ることがあります。
他の利用者に公開されることはありません。
```
- ⚠️「**見ることがあります**」と正直に書いてある。DBに入っている以上「見ません」とは書けない
- 「不具合の調査と難易度の調整のために」＝**利用目的の限定**。⚠️これ以外に使わない
- **既存プレイヤーへの再表示**: `progress.disclaimerRev`(既定0)が `DISCLAIMER_REV` 未満なら再表示する
  (実装済み。`index.vue` / `storage.ts`)。⚠️再表示のときは**理由を1行添える**
- ⚠️開示の内容を変えたら `DISCLAIMER_REV` を上げる。⚠️上げずに文面だけ変えない
- ⚠️**プライバシーポリシーへの利用目的の追記が発生する**(CONSTRAINTS §3-6・§5-6)。
  ゲームの外の作業なので、⚠️パージのときに**戻す作業が1件増える**
