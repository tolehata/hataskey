# 花常 設計制約(法務・ライセンス・パージ容易性)

2026-07-20 の調査(法務3レンズ・アーキテクチャ2件、一次情報当たり)の結論。
**イベント機能・交換所・集会要素の実装は、本書の制約を満たす形でのみ行う。**

⚠️本書は**法的助言ではない**。§4 の論点は実装着手前に人間の判断が必要。

---

## 0. 不変条件(これを崩すと全章の結論が変わる)

| # | 不変条件 | 崩したときに起きること |
|---|---|---|
| **INV-1** | ゲーム内の通貨・ポイント・報酬は**無償配布のみ**。有償取得経路をゼロにする | 資金決済法(前払式支払手段)の届出・供託論点が発生 |
| **INV-2** | 報酬・アイテムは**換金不可・ユーザー間譲渡不可**。外部で価値を持つ財と交換しない | 「財産上の利益」性が生じ、賭博罪・RMTの議論領域に入る |
| **INV-3** | **hataskey本体の有料機能・寄付と、ゲーム内の優遇を一切連動させない** | 景表法の**取引付随性**が発生し、景品規制が現実の論点になる |
| **INV-4** | ゲームの挙動は**寄付者/非寄付者で完全に同一**。寄付の訴求文言でゲームに言及しない | 「寄付するとゲームで有利」と読める表示自体が取引付随性の証拠になる |

⚠️**旗鯖は実際に「寄付 → 機能制限緩和」を運用している。**
したがって INV-3 / INV-4 は仮定ではなく**現実の必須要件**である。
具体的な遵守事項は **§4.1A「寄付の壁」(W-1〜W-6)** に定めた。実装前に必ず読むこと。

### 危険ラインの一言まとめ
危なくなるのは「無償かどうか」ではなく、次の4つが起きた瞬間:
1. **金銭的対価がゲームに接続した**
2. **報酬に換金/譲渡可能性が生まれた**
3. **告知した内容と実装が食い違った**
4. **集会機能に1対1の非公開フリーテキスト経路ができた**

## 1. 実装してよいもの

### イベント本体
- 期間限定イベント(参加条件に金銭的対価を要求しない)
- イベント限定ステージ / 限定シナリオ / 限定報酬(ゲーム内でのみ消費・表示)
- 抽選・ランダム要素(**敗北時に何も失わない**構造であること)
- **イベント告知の常設ページ**: 開始/終了日時(⚠️**タイムゾーン明記**。⚠️画面では**日本語で「日本標準時」**と書き、
  `JST`/`+09:00` と書かない)、報酬内容、参加条件、終了後の報酬の扱いを**イベント開始前**に掲示。
  ⚠️表記は EVENTS.md §2.5(「**開催時間**」に統一)と §11.1(告知文の雛形)に従う
- 変更履歴ページ(仕様変更・不具合対応の履歴。表示の正確性を示す実務上の反証資料になる)

### 交換所(この形なら安全)
```
[無償のイベント行動] → [イベントポイント(無償配布のみ・単一残高)] → [ゲーム内アイテム]
```
必須要件:
- ポイント取得経路は**イベント内の無償行動のみ**(有償経路をUIごと存在させない)
- ⚠️**有償/無償ポイントの区別という概念自体を持たない**(残高は1種類だけ。将来も混在できない構造にする)
- 交換先は**ゲーム内で消費・装飾されるだけ**のアイテム
- **交換レートを事前に固定表示**し期間中に変更しない(変更するなら事前予告)
- ポイントに有効期限を設けるなら**取得時点で明示**
- ⚠️**他ユーザーへの譲渡UIを持たない**(APIレベルでも実装しない)

### 集会(この形が最も安全)
**「非同期・共通目標・定型表現のみ」**。
- **共通目標への貢献値加算型**(全員の合計がしきい値に到達すると全員に同じ報酬)
  → 敗北時に失うものがなく参加も無償なので、賭博罪の要件を欠く
- 意思表示は**定型スタンプ/絵文字/定型文の選択のみ**(⚠️フリーテキストを介在させない)
- 表示する他ユーザー情報は**hataskey上で既に公開されている情報のみ**(表示名・アイコン・ユーザー名)
- 参加/不参加を選べる(集会に出ていることが不可視でも成立する設計)

### アーカイブ
- **過去イベントの閲覧**(ストーリー再読・記録閲覧)。報酬を伴わない「読み物としての復刻」は
  法的接点・不公平感ともに**最小で、最も安全な復刻手段**
- 過去イベント報酬を後から**無償で**取得可能にする設計も、対価がない限り可

## 2. 実装してはならないもの

### 2-1. 金銭・経済(致命度: 最高)
| 禁止 | 理由 |
|---|---|
| 有償ポイントと無償ポイントの同一残高・同一UIでの混在 | 有償分が混じり区別が不明確だと残高全体が前払式支払手段扱いとなりうる |
| 報酬・ポイントの現金/電子マネー/外部財との交換導線 | 換金性が生じた時点で景表法・賭博罪の双方でリスクが跳ね上がる |
| アイテムのユーザー間譲渡/トレード | RMT市場が事実上成立し「財産上の利益」性が認められる方向に傾く |
| 有料プラン加入者・寄付者だけのイベント/限定報酬/交換所優遇 | 取引付随性・顧客誘引性が揃い、景品類に該当する余地が高い。**最も避けるべき設計** |
| 有償要素が絡む状態でのN種コンプリート型交換 | 懸賞景品制限告示第5項の「カード合わせ」類型。該当すれば**金額の多寡を問わず全面禁止** |
| 寄付者へのゲーム内リターン | 寄付に対価性が生じ、取引付随性が発生する方向に傾く |

⚠️**コンプリート型(絵合わせ)の交換は、無償であっても本作では実装しない。**
「完全無償なら適法」と明言した消費者庁の公表文書を特定できなかったため(§4-4)、安全側に倒す。

### 2-2. 表示・告知(致命度: 高。**無償でも回避できない**)
| 禁止 | 理由 |
|---|---|
| 「二度と手に入りません」と表示して後から同一報酬を再配布 | 有利誤認の典型類型 |
| **排出率・獲得確率の表示** | 表示と実装の乖離は課徴金事案の中心論点。⚠️**表示しない設計が最も安全** |
| 報酬内容を告知後に事前予告なく減額・削除(不具合対応を除く) | 有利誤認および不公平感の主因 |
| 「ランキングは無い」と謳いつつ集会で貢献度順位を可視化 | 実質ランキングであり方針の自己矛盾 |

### 2-3. 集会・未成年保護・プライバシー(致命度: 高)
| 禁止 | 理由 |
|---|---|
| 面識のない未成年と成人が**1対1で私的にやり取りできるフリーテキスト経路** | 出会い系サイト規制法上の該当性の議論を招きうる |
| 外部SNSのID・連絡先を交換できる仕様(自由入力欄を含む) | プラットフォーム実務では一律禁止が標準 |
| 他ユーザーの非公開情報の表示・推知(メール/生年月日/非公開フォロー関係/最終ログイン時刻等) | 個人情報保護法の利用目的・第三者提供の論点 |
| 常時プレイ状況の他者への無条件公開 | 行動追跡と受け取られやすい。オプトアウト無しは不可 |

### 2-4. ライセンス(致命度: 高)
| 禁止 | 理由 |
|---|---|
| hataskeyのビルドに取り込まれた花常を含む**配布物全体**を「MIT」として提供 | GNU公式FAQ: GPL互換コードを取り込んでも「その全体はGPLの下でライセンスされねばならない」 |
| AGPL §13 のソース提供義務を「商用だから」を理由に免れようとする | 条文にそのような区別はない |
| import/バンドルした状態でゲーム部分をAGPL対象外と主張しソース提供を拒む | 結合著作物として扱われる |
| 利用規約でAGPL §13の義務を無効化・制限する | §13の義務を狭める追加条件は付せない |
| AI生成の物語・画像について、**著作権が確実に発生していると断定して第三者に権利主張** | 日本法上、AI生成物は著作物性が認められない可能性がある(文化庁の整理) |

### 2-5. アーキテクチャ(致命度: 中。技術的負債)
⚠️**すべて「後から剥がせなくなる」もの。** 実コード調査に基づく。

## 4.1A 旗鯖の寄付構造と、そこから導かれる「寄付の壁」(★実装必須)

### 確認された事実(2026-07-20・運営者による)
- 旗鯖は**寄付を受け付けている**
- **寄付者には機能制限の緩和がある**
- 寄付は**サーバー(法人・事業体)宛ではなく個人宛**
- サーバー側の特典も一部あるが、**商用運用ではない**

### これが意味すること
景表法の「景品類」は ①顧客誘引の手段 ②**取引に付随** ③経済上の利益 の3要件で判断される。
本件で重要なのは②。**「寄付 → 機能制限緩和」という対応関係が既に存在する**以上、
純粋な任意の寄付(対価性なし)とは言い切れず、**取引に類する関係がプラットフォーム上に既にある**と
見るべきである。したがって:

> ⚠️**ゲーム内の報酬が寄付者に少しでも有利に働いた瞬間、
> 「寄付という取引に付随した経済上の利益の提供」= 景品類の提供、という整理が現実味を帯びる。**

逆に言えば、**ゲームが寄付階層と完全に無関係であれば、報酬は「取引に付随していない」**。
全ユーザーに等しく無償で提供されるものは、そもそも取引に紐づいていないからである。

⚠️また、**「個人宛の寄付だからサーバーとは別」という切り分けは、思ったほど守ってくれない**可能性がある。
同一人物がサーバーを運営し、その人への寄付でそのサーバーの機能が緩和されるなら、
**実態として役務の対価と評価される余地**がある。形式的な主体分離で規制を回避できるとは考えないこと
(調査結果の conditional にも同旨の指摘あり)。

### 結論: 「寄付の壁」を設計として明示する(⚠️実装必須)

**花常は、寄付・機能制限緩和の仕組みと一切接続しない。** 具体的に、以下をすべて満たすこと。

| # | 壁 | 内容 |
|---|---|---|
| W-1 | **ゲーム内容の同一性** | 寄付者/非寄付者で、遊べるステージ・イベント・報酬・交換所・在庫上限・保存容量が**完全に同一**。分岐するコードを書かない |
| W-2 | **参照禁止** | ゲームのコードから**寄付状態・ロール・プラン・機能制限に関する情報を一切読まない**。⚠️APIで取得できてしまう場合でも触らない(将来の誘惑を断つため、取得箇所を作らない) |
| W-3 | **機能制限緩和の対象外** | 寄付特典のリストに**ゲームに関する項目を絶対に入れない**(「花常の〇〇が使える」等) |
| W-4 | **訴求文言の分離** | 寄付の募集・説明文で**ゲームに言及しない**。⚠️「寄付するとゲームで有利」と読める表示は、それ自体が取引付随性・顧客誘引性の証拠になる |
| W-5 | **告知の分離** | イベント告知に寄付への導線を置かない。逆も同じ |
| W-6 | **集会要素での平等** | 集会の貢献値・報酬配分も寄付状態と無関係。寄付者バッジ等を**ゲーム内で表示しない** |

⚠️Codex: W-2 は実装レベルの規律である。
**寄付・ロール・プラン判定のAPIをゲームから呼ぶコードを書かないこと。**
「将来使うかもしれない」という理由でも取得しない。

### 商用ではないことの効果
- **特定商取引法**の表示義務は、通信販売等の取引がない以上、原則として生じない(§3の3-6とは別論点)
- ただし ⚠️**AGPL §13 のソース提供義務は商用/非商用を問わず発生する**(§4-7)。
  非商用であることはライセンス義務を免除しない
- 景表法の「事業者」性は営利・非営利を問わず認められうるため、
  **「商用でないから景表法は関係ない」とは考えないこと**

### 運営方針(2026-07-20 確定・恒久)
> **花常には有料要素を最初から一切取り入れない。これは今後も変わらない。**
> **すべての要素を無料で遊べ、寄付によって優劣が変わることはない。**

これは現状の説明ではなく**恒久的な運営方針**である。したがって:
- §0 の INV-1〜INV-4 と本節の W-1〜W-6 は、**将来も緩和されない前提**で実装してよい
- 有償経路を後から追加できる「拡張性」を残す必要は**ない**。
  ⚠️むしろ残さないほうがよい(§1の交換所要件「有償/無償の区別という概念自体を持たない」と一致)
- §4-1 にあった唯一の分岐点(寄付特典にゲーム項目を入れる場合)は、**方針として発生しない**

⚠️Codex: この方針により、**課金・スタミナ・ログインボーナス強制・確率表示・
有償通貨に類するものを、イベント機能であっても一切実装しない**。
「イベントだから」は例外の理由にならない。

## 5. パージ容易性の構成ルール(⚠️これに従って実装する)

目標は「完全独立」ではなく**「分離しやすさ」**。過剰設計はしない。

### 5-1. 本体側に入れてよい追記の上限
| 場所 | 上限 |
|---|---|
| `src/router.definition.ts` | ⚠️**1ブロックのみ**。ルートは1本に絞り、画面遷移は内部ステートで切り替える(stacking-gameは5ルートに割って追記が5ブロックになっている) |
| `src/pages/games.vue` | カード1枚(約10行)。可能なら**データ駆動化**(`const GAMES=[{to,emoji,title,sub}]` + `v-for`)して、追加削除を配列1要素の増減で済むようにする |
| その他の本体ファイル | ⚠️**追記ゼロ**。locale・PREF_DEF・local-storage・achievements・navbar・vite.config はすべて触らない |
| backend | ⚠️**変更ゼロ** |

### 5-2. ゲーム側の構成
```
packages/frontend/src/pages/hanaawase/     ← ゲームは全部ここに閉じる
  index.vue        ← エントリ(シーン制御のみ)
  ...(§11.3 の構成)
packages/frontend/assets/hanaawase/        ← アセット(vite.config.ts:163 が丸ごとエイリアス済み・追記不要)
```
- **本体依存は `definePage` / `misskeyApi` / `MkButton` 程度に限定**する。
  ⚠️`drop-and-fusion.game.vue` が os/store/$i/sound/achievements/prefer と**8種類**に依存している状態は再現しない
- ロジックの別パッケージ切り出しは**不要**。`misskey-bubble-game` の例では切り出しても本体側のVueページが丸ごと残り、
  パージ容易性はほぼ改善しない。frontend 内の純TSモジュールで十分

### 5-3. 保存(⚠️これ一択)
- **`i/registry` を自前 scope で直接叩く**。先例: `src/utility/clicker-game.ts:26-56`(scope `['clickerGame']`)、
  `src/utility/hatady-prefs.ts`(scope `['client','hatady']`)
- 依存は `misskeyApi` + `miLocalStorage` の2つのみ。**バックエンド変更ゼロ**になる
- ⚠️`prefer`(PREF_DEF)は使わない(§2-5)

### 5-4. i18n(⚠️本体localeを使わない)
- ゲーム内文言は**ゲーム側に閉じ込める**。先例: **Hatady が本体localeを一切使わず自前ja/enを実装済み**
  (`src/utility/hatady-prefs.ts:17,49,79` / `src/pages/hatady.vue:391,804`)
- ゲームハブ `games.vue` も i18n を import しているのに未使用で全文言が日本語リテラル。**ハブ追加も locale 不要**

### 5-5. 撤去メモを残す
エントリポイント(`games.vue` のカード、`router.definition.ts` の該当ブロック)に、次の形のコメントを入れる:
```
// 旗鯖fork: 花常 — 削除時は src/pages/hanaawase/ + assets/hanaawase/ + 本ブロックのみ
```
後日のパージが機械的になる。

### 5-6. パージ手順(⚠️「ファイルを消して終わり」ではない)

⚠️不可逆な操作を含む。**実行前に対象と影響範囲を運営者に示して確認を取ること**。

| # | やること | 備考 |
