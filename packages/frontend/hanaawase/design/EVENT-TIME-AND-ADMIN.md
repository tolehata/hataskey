## ⚠️最重要の発見：CONSTRAINTS を破らずに「個人別の詳細把握」ができる

利用者は「管理者が個人別にプレイ状況を詳細把握」を選択した。設計側は当初「backend実装が必要でパージ容易性が崩れる」と伝えたが、**それは誤りだった**。

- 花常の保存先は registry（`storage.ts` scope `["client","hanaawase"]`）＝**`registry_item` テーブルに既に入っている**
- ⚠️**アプリのAPI経由では取れない**（`i/registry/get.ts` は `me.id` 固定・`admin/` に registry 系エンドポイントは存在しない）
- ⚠️**しかし DB を直接引けば、コードを1行も書かずに全ユーザー分が読める**

```sql
SELECT u.username, r.key, r.value, r."updatedAt"
FROM registry_item r JOIN "user" u ON u.id = r."userId"
WHERE r.scope = '{client,hanaawase}' AND r.domain IS NULL;
```

⚠️**CONSTRAINTS が禁じているのは「backendへの新エンドポイント／エンティティ／マイグレーション」であって、運営者が自分のDBを読むことではない。** よって**制約を1つも破らずに、利用者の決定をそのまま満たせる**。

## 1. 管理者導線：推奨案

**案A（運用SQL）＋ 案C（匿名集計）＋ 案B（本人による書き出し）の組み合わせ。⚠️案D（backend実装）は採らない。**

| | backend変更 | パージ影響 | 個人別 | コスト |
|---|---|---|---|---|
| **案A 運用SQL** | ゼロ | **なし** | **可能** | 極小 |
| **案C 匿名集計JSON** | ゼロ | なし | 不可 | 極小 |
| **案B 本人が書き出す** | ゼロ | なし | 本人のみ | 小 |
| 案D 完全backend実装 | エンドポイント＋SDK再生成＋マイグレーション | ⚠️**崩壊** | 可能 | 大 |

- **日常は案C**（人気の面／詰まる面／離脱点は個人を出さずに全部わかる）
- **必要が生じたときだけ案A**（不具合の再現調査）
- **案Bを併設**（設定に「記録を書き出す」。管理者がDBを引く回数自体が減る）

### ⚠️案Dの落とし穴（記録として残す）
1. `iAmModerator` は**フロントの表示制御であって認可ではない**。データがAPIから返る以上、非モデレータも直接APIを叩けば取れる。個人別を守るにはサーバー側の認可が必須＝それが案Dのコストの本体
2. ⚠️**個人別データを静的JSONに置くのは絶対禁止**（`/client-assets/` はURLを知れば誰でも読める）。この経路に載せられるのは匿名集計だけ

## 2. 収集項目の最小化 ＝「1フィールドも足さない」

目的（①難易度調整 ②離脱点 ③不具合再現 ④イベント周回量）は、**既存の3キーで全部達成できる**。

**集めない・見ないと決めるもの**
- ⚠️**1手ごとの操作ログ・盤面ログ** — そもそも保存していない。**新設しない**
- ⚠️**`progress.choices`（物語の分岐）を個人に紐づけて見る** — 嗜好そのもので感度が高い。見るなら**匿名の比率のみ**
- ⚠️**花常の外の情報**（フォロー関係・ロール・寄付状態） — W-2 により引かない。SQLのJOINも `username` の解決までに留める
- ⚠️**IP・UA・端末情報** — 一切扱わない
- ⚠️`updatedAt` は**最終プレイ時刻に相当する**（CONSTRAINTS §最終ログイン時刻の推知に触れる）→ **他者に見せない**

## 3. ⚠️初回の注意書き（§3.59）への追記が必要
現行の開示は「生成AI」と「架空」の2ブロックだけで、**データの扱いの開示が無い**。3ブロック目を4行で足す：

> 遊んだ記録（進み具合・遊んだ回数・設定）は、このサーバーの
> あなたのアカウントに保存されます。サーバーの管理者は、
> 不具合の調査と難易度の調整のためにこれを見ることがあります。
> 他の利用者に公開されることはありません。

- ⚠️「**見ることがあります**」と正直に書く。DBに入っている以上「見ません」とは書けない
- 「不具合の調査と難易度の調整のために」＝**利用目的の限定**。これを書いた以上それ以外に使わない
- ⚠️同意チェックボックスを足さない／文字を小さくしない／「はじめる」だけを目立たせない

**⚠️既存プレイヤーへの再表示が必要**（`disclaimerSeen: true` の人には二度と出ない）。`progress.disclaimerRev`（既定0）を足し、`DISCLAIMER_REV` 未満なら再表示。

> **2026-07-27 追記: 利用者が承認し、実装済み。** `index.vue`（`DISCLAIMER_REV`・再表示の理由行）
> `storage.ts`（`disclaimerRev` の既定0・マージは大きいほう）。⚠️文面を変えたら `DISCLAIMER_REV` を上げること。

## 4. 運用として決めておくこと（案A採用時）
- 目的を限定：不具合調査と難易度調整のみ
- アクセスできる人を限定：**DBに入れる人＝サーバー管理者**（モデレータ全員ではない）
- 個人別を引いたら**誰がいつ何のために引いたかを残す**（統制の実体は「記録が残る」こと）
- ⚠️結果を**個人が識別できる形で公開・投稿しない**（スクリーンショット含む）

# 6. 「開催時間」への表記統一

⚠️**実装コードにはまだ1件も無い**（`src/pages/hanaawase/` を grep して0件）。**いま統一すれば後から直す作業は発生しない。イベント実装前が最後のタイミング。**

## 6-1. 役割ごとに正本を1語ずつ決める
| 役割 | 採用語 | 廃止 |
|---|---|---|
| 時間の範囲（見出し） | **開催時間** | 開催期間／会期／開催時期／期間 |
| 範囲内にある状態 | **開催中** | （据え置き。別概念なので潰さない） |
| 終わりまでの猶予 | **開催時間 のこり N日** | 残り期間／あと◯日（単独） |
| 開催前 | **開催時間 N月N日から** | 近日開催／まもなく |
| 終了後 | **開催時間 終了しました** | 終了間近／終了済み |
| 2回目以降 | **再びの開催** | 復刻（⚠️UIには出さない。ドキュメント内の運用語としては残す） |

⚠️**JSONのキー名（`runs`/`start`/`end`/`label`）は改名しない**。管理者が触るスキーマを日本語表記の都合で変えると互換が切れる割に得るものがない。統一は**日本語表記（ドキュメント＋UI文字列）に限る**。
⚠️台詞タグ名（`序盤`/`中盤`/`終盤`）も変えない（`event.json` のデータに埋まるため）。
⚠️「開催時間」は本来「営業時間」に近い含みを持つので、**必ずラベル＋値の形で出す**（値を省いて孤立させない）。

## 6-2. 表示形式は3つだけ
**(A) 完全表記**（告知・扉）
```
開催時間
2026年8月1日(土) 0:00 から
2026年8月18日(火) 0:00 まで（日本標準時）
```
⚠️**タイムゾーンを画面に明記**（CONSTRAINTS の必須要件）。`JST`/`+09:00` でなく日本語で。⚠️端末TZに依存させず `daily.ts` の `JST_OFFSET_MS` 方式を流用。

**(B) 一行表記**（イベントホーム）
| 状態 | 文字列 |
|---|---|
| 開催前 | `開催時間 8月1日から` |
| のこり2日以上 | `開催時間 のこり 6日` |
| 同日中に終わる | `開催時間 本日まで` |
| 終了後 | `開催時間 終了しました` |

⚠️**「のこり 0日」を出さない**（最終日は「本日まで」）／色は `--sub`・赤字や点滅を使わない／⚠️**「お見逃しなく」「今だけ」を書かない**（復刻があるので焦らせる理由がない）／⚠️残り日数は**JSTの日付境界で数える**（時刻差を86400000で割らない）。

**(C) アーカイブ**：季節表記（「初夏」）を主に残す。扉を開いたときだけ (A) を「これまでの開催時間」として出す。

## 6-3. 復刻（`runs` 複数）の表示規則
1. 現在時刻が入っている run を「開催時間」として出す
2. 無ければ**未来で最も近い** run を「開催時間 N月N日から」
3. 未来も無ければ「開催時間 終了しました」

過去の run は**扉の中でだけ**列挙。⚠️`runs[].label` はそのまま画面に出るので、**`index.json` に書く値を「初回」「再びの開催」にする**（コード側で変換する分岐を書かない＝パージが重くなる）。

## 6-4. ⚠️`index.json` の取得規律（緊急終了が効くための生命線）
```ts
await fetch('/client-assets/hanaawase/events/index.json', { cache: 'no-store' });
```
- ⚠️`no-store` を**必ず**（`ClientServerService.ts` が `max-age=604800` を返すため、素で fetch すると最大7日効かない）
- SWは無関係（`sw.ts` はHTMLのみ横取り。確認済み）
- 再取得：マウント時／イベント画面へ入るたび／`visibilitychange` で visible／リザルト確定後（メモリキャッシュTTL 60秒）
- ⚠️**プレイ中は判定しない**。緊急終了が走っても遊んでいる1局は最後まで遊ばせ報酬も付与。⚠️局中に盤面を殺すと「データが消えた」と受け取られる
- ⚠️取得失敗時は**静かに無効化**し、**前回の index を流用して「開催中」を続けない**（fail-closed。fail-openだと緊急終了が効かない端末が生まれる）

## 6-5. ⚠️スキーマの穴（要修正）
`EVENTS.md` の例は `"end": "2026-08-17T23:59+09:00"`。判定を `now <= end` にすると **23:59:01〜23:59:59 の59秒が宙に浮き**、`archiveFrom: "08-18T00:00"` との間に空白ができる。
→ **判定は `start <= now && now < end` に統一し、`end` には終了日の翌日 `00:00+09:00` を書く**。`archiveFrom` を `end` と同値にすれば空白も消える。⚠️`EVENTS.md` §2 の例示JSONを直すこと。
