hataskey games 新作・3マッチパズル。本書は**実装AI(Codex等)がこの1枚だけで作業できる**ことを目的とした自己完結文書である。
リポジトリ規約・統合ポイント・落とし穴をすべて本書に含める。**本書と実コードが矛盾した場合は実コードを正とし、本書の該当箇所を疑うこと。**

## 0. リポジトリ基礎知識(最初に読む)

### 0.1 これは何のリポジトリか
Misskey/CherryPick フォーク「hataskey」(旗鯖専用SNS)。pnpm monorepo。
本ゲームは **frontend のみ**で完結する(v1 でバックエンド変更は一切不要)。

```
packages/frontend/src/
  pages/           ← ページ。既存ゲーム: drop-and-fusion.vue, stacking-game.vue 等
  pages/games.vue  ← ゲームハブ(ここにカード追加)
  components/      ← 共有コンポーネント
  utility/         ← ロジック・ヘルパ
  router.definition.ts ← ルート定義
packages/frontend/assets/   ← 静的アセット。/client-assets/ で配信される
```

### 0.2 コマンド(検証は必ずこれで)
```bash
pnpm --filter frontend typecheck   # vue-tsc --noEmit。必ず通すこと
pnpm --filter frontend eslint
cd packages/frontend && pnpm vitest run src/path/to/foo.test.ts  # 単体テスト
```

### 0.3 コード規約
- Vue 3 Composition API + `<script setup lang="ts">` + CSS Modules(`<style lang="scss" module>`)
- 各ファイル先頭に SPDX ヘッダ:
  ```
  <!--
  SPDX-FileCopyrightText: Tolehata and hatasaba-project
  SPDX-License-Identifier: AGPL-3.0-only
  -->
  ```
- アイコンは Tabler (`<i class="ti ti-..."></i>`)
- テーマ変数: 色は `--MI_THEME-*`、レイアウトは `--MI-*`。ただし本ゲームは独自スコープ(§11.4)を持つ

### 0.4 ⚠️Codex: このリポジトリ固有の落とし穴(全部実在の事故例)
1. **CSS Modules の動的キーは解決されない。** ビルドプラグインが `$style.foo` を静的に解決するため、
   `$style[someVar]` や `{ [$style.x]: cond }` は**クラスが付かない**(エラーも出ない)。
   → 分岐は `v-if`/`v-else` で静的参照するか、`data-*` 属性 + 属性セレクタで書く
2. グローバル `<style>`(module なし)からハッシュ化されたモジュールクラス名は狙えない。`data-*` を使う
3. `computed` の中で副作用(保存処理等)を起こさない
4. `position: fixed` 要素の祖先に `transform`/`animation` があると fixed の基準がその祖先になる。
   ツールチップ類は `<Teleport to="body">` で逃がす
5. アニメ中の要素を `v-if` で unmount→remount すると入場アニメが再発火する。
   一覧の再取得中に v-if でローディング表示に切り替える構造は再アニメ事故のもと(§9.6)

### 0.45 ⚠️Codex: 設計側が実際に踏んだ地雷(この文書を書く過程で起きた事故)

§0.4 はリポジトリ固有の罠。こちらは**日本語テキストと環境の扱い**で実際に起きた事故。
本作は20万字の日本語を扱うため、**Codexも高確率で同じ穴に落ちる**。

#### 1. ⚠️Git Bash の `grep` は日本語の文字クラスを壊す(最悪の事故)
`grep -o "【[^】]*】"` のような**多バイト文字を含む文字クラス**は、Git Bash の grep が
**バイト単位で処理して誤った結果を静かに返す**。エラーは出ない。

- **実際の被害**: 本文の表情マーカーを数えたところ「ほぼ存在しない」という結果が出た。
  それを信じて「本文に表情指定が入っていない」と**誤った報告をし、誤った前提で仕様を1節書いた**。
  実際には**693個すべて入っていた**
- **対処**: 日本語を含む検索・置換・カウントは **PowerShell の .NET 正規表現**を使う:
  ```powershell
  [regex]::Matches([System.IO.File]::ReadAllText($path), '【[^】]*】').Count
  ```
- ⚠️`grep` の結果が「思ったより少ない/ゼロ」のときは、**結論を出す前に別の手段で数え直す**こと。
  日本語検索でゼロが返ったら、まず道具を疑う

#### 2. ⚠️PowerShell のファイル書き込みは既定で文字化けする
`Set-Content` / `Add-Content` は**システムANSI**、`Out-File` / `>` は**BOM付きUTF-8**になる。
どちらも日本語Markdownを壊す。

- **対処**: 必ず BOM なし UTF-8 で書く:
  ```powershell
  $enc = New-Object System.Text.UTF8Encoding($false)
  [System.IO.File]::WriteAllText($path, $text, $enc)
  ```

#### 3. ⚠️UNC パス(`\\wsl.localhost\...`)では Bash のファイル操作が失敗する
本リポジトリは Windows から `\\wsl.localhost\ubuntu\...` で見える。この経路では
Bash ツールの `mkdir` が `Read-only file system` で落ちる。

- **実際の被害**: `mkdir` が失敗したのに続けて `cp` を実行し、
  **ディレクトリのつもりでファイルを作ってしまった**(`design` という名前のファイルができた)
- **対処**: UNC 上のディレクトリ作成・コピー・リネームは **PowerShell** で行う。
  読み取り(Read/Grep/Glob)と `git` は Bash で問題ない
- ⚠️複合コマンドは `set -e` を付けても**前段の失敗に気づかないことがある**。作成後は必ず一覧で確認する

#### 4. ⚠️長い日本語を一度に書くと、外国語が混入する
これは**生成モデル共通の失敗**であり、Codex も必ずやる。

- **実際の被害**: 待機会話250本を書いたとき、日本語の文中に
  `traffic` / `continuar`(スペイン語) / `water` が紛れ込んだ。
  過去には本文に**ハングル**(`회転`←「回転」)も混入していた
- **対処**: 長い日本語を書いたら、**必ず機械で自己検査する**:
  ```powershell
  # ハングル・キリル等の混入検出
  if ($t -match '[가-힯ᄀ-ᇿА-Яа-я]') { "混入あり" }
  # 日本語行に紛れたラテン文字(コード片・英字の固有名詞は除外して判断)
  ```
- ⚠️`story.ts` へ本文を移す作業(P7)は**この事故が最も起きやすい工程**。
  移したあと、元の Markdown と**文字数・行数を突き合わせて一致を確認**すること

#### 5. ⚠️長文を書くと重複する
250本を一度に書いたら、**別プールに完全に同じ一文**が入った(表示時に同じ文が2行並ぶ事故)。

- **対処**: 大量のテキストデータを作ったら、**必ず重複検査を機械でかける**
  ```powershell
  $body | Group-Object | Where-Object Count -gt 1
  ```

#### 6. ⚠️設定にない属性を勝手に足してしまう
待機会話に「眼鏡を上げる。」と書いたが、**若菜に眼鏡の設定は存在しない**(立ち絵と矛盾する)。

- **対処**: キャラクターの身体・持ち物・癖を書く前に、**BIBLE §5 と SPEC §12.7 を検索して確認**する。
  「それらしいから」で足さない。⚠️特に画像生成のプロンプトを組むときに致命傷になる

#### 7. ⚠️置換は「消えたこと」ではなく「正しくなったこと」を確認する
誤字を置換したあと「元の文字が消えたか」だけを確認して、**置換結果が壊れているのに見逃した**
(`和集合` にするつもりが `和合合` になっていた)。

- **対処**: 置換後は**対象行をそのまま出力して目視**する。存在チェックだけで済ませない

### 0.46 ⚠️Codex: 失敗の「型」(個別の事故より、こちらのほうが重要)

§0.45 は個々の事故。こちらは**この企画とフォーク本体の開発で繰り返し起きた失敗のパターン**。
同じ型の失敗は、状況を変えて何度でも起きる。

#### 型1. 検証せずに前提を置き、その上に積み上げる
- 道具の結果を信じて「本文に表情指定がない」と判断し、**誤った前提で仕様を1節書いた**(§0.45-1)
- 本文の場面を確認せずに背景を6枚と決め、あとで**12種必要だと判明**した
- 実測せずに「各月2万字」と書いたが、実際は**約3,300字**(6倍のずれ。§2.3で訂正済み)
- **対処**: 数値・存在・網羅性を主張する前に、**必ず数える/検索する**。
  「たぶんこうだろう」で仕様に書かない。⚠️特に「全部」「〜が無い」「〜件ある」は必ず実測してから書く

#### 型2. 変更したのに、依存している場所を直さない(★最頻出)
実際に起きたもの:
- チュートリアルを `hintsSeen` に変えたが、**§7の保存スキーマは `hintDone` のまま**だった
- 背景を12種に増やしたが、**§12.2の支給マニフェストは6枚のまま**だった
- 道具名を「鋏/手直し/打ち水」に変更したが**デザイン依頼を更新せず**、
  handoff が「ハンマー/入替/シャッフル」で返ってきた
- ゲーム名を「花常」に変えたら、**ハッシュタグ禁止の理由が無効化**した
  (理由が「はなあわせは一般語だから」だった)
- **対処**: 何かを変えたら、**その語で全文検索して波及先を潰す**。
  ⚠️特に「識別子・スキーマ・アセット名・固有名詞」を変えたときは必ず grep すること。
  仕様に書いた**理由**も、前提が変われば壊れる

#### 型3. 既存のものを流用して、その前提ごと持ち込む
フォーク本体で実際に起きたもの:
- モーダル用の全幅ボタン `.primaryBtn` をツールバーに流用し、**レイアウトが崩れた**
- 一覧に入場アニメを付けたら `transform` が発生し、
  子孫の `position: fixed` の基準が壊れて**ツールチップがずれた**(§0.4-4 の実例)
- 読み込み表示を `v-if` で切り替えたら、**再マウントで入場アニメが再発火**した(§0.4-5 の実例)
- **対処**: 流用するときは「その要素が前提にしている文脈」まで見る。
  ⚠️**自分が入れた変更が原因の回帰**は、原因を外部に探しがちなので特に疑うこと

#### 型4. 症状から原因を推測して誤診する
- 動的 import の失敗を **CORS だと誤診**した。実際は**古いチャンクのキャッシュ**で、リロードで解消した
- **対処**: 推測で修正を入れる前に、**最も安い確認**(リロード/再ビルド/別環境)を先に試す。
  存在しない問題を「直して」しまうと、余計な変更が残る

#### 型5. 否定形だけの指示は暴走する
- キャラ生成で「マズルを描かない」とだけ指示したら、**ケモミミの人間**になった。
  禁止だけ伝えて、**代わりに何を描くかを指定しなかった**のが原因
- **対処**: 禁止を書いたら、必ず**望ましい代替を同じ場所に書く**。
  ⚠️これは画像生成プロンプト(§12.7)で最も効く

#### 型6. コストの見積もりを外す
- 調査を1回回したら**100体規模のサブエージェントが動き、利用枠を使い切った**。
  さらに再開して追撃し、二重に消費した
- **対処**: 大量に枝分かれする操作は、**規模を見積もってから**着手する。
  枠を使い切ったあとの「もう一度」は、たいてい状況を悪くする(§0.5)

#### 型7. 生成した長文を自分で検査しない
- 日本語の長文に**英語・スペイン語・ハングルが混入**した
- 大量のデータを書いたら**完全な重複**が生まれた
- 設定に無い属性(若菜の眼鏡)を**それらしいという理由で足した**
- **対処**: 生成物は**必ず機械で検査してから完成とする**(§0.45-4,5,6)。
  ⚠️自分が書いたものを「たぶん大丈夫」とみなさない

### 0.49 ⚠️Codex: 「Error submitting message」が頻発するときの対処(2026-07-21 追記)

**運営者から報告あり**:
> 「Error submitting message が頻発して、1つの表情差分を作った後に止まってしまう」

⚠️これは**リクエストサイズの上限を超えている**ことによるほぼ確定的な事象。以下の対策で解決する。

#### 0.49.1 ⚠️参照画像は必ず `ref/thumb/` の軽量版を使う(★最重要)
`ref/wakana.png`(1.78MB) と `ref/ren.png`(1.80MB) は**原本**であり、参照渡し用ではない。
運営者側で軽量サムネイルが用意されている:
```
ref/thumb/wakana.jpg  (54KB / 358x512 JPEG q85)
ref/thumb/ren.jpg     (64KB / 430x512 JPEG q85)
```
- **`-i` フラグで渡すときは必ず `ref/thumb/wakana.jpg` / `ref/thumb/ren.jpg` を使う**
- ⚠️**`ref/*.png` を `-i` で渡さない**。1リクエストで3〜4MBになり詰まる
- 画風判断には**この解像度で十分**。細部が要る場面は原本を目視するだけ

#### 0.49.2 1回のリクエストを軽くする
| やること | 効果 |
|---|---|
| ⚠️**参照画像は1〜2枚に絞る**(人間キャラ=wakana.jpg のみ / 獣人=wakana.jpg + ren.jpg) | リクエスト最小 |
| **プロンプトを短くする**(SPEC全体をコピペしない。必要な節だけ抜粋) | コンテキスト削減 |
| **1リクエスト1画像**(複数枚を1つのプロンプトで作らない) | 応答サイズ削減 |
| セッションが長くなったら**新規セッションに切り替え**(過去やり取りは`WORKLOG`で引き継ぐ) | 履歴肥大解消 |

#### 0.49.3 それでも Error が出るときの手順
1. **同じリクエストを3回試して失敗**するなら、参照画像を1枚に減らして再試行
2. それでも失敗するなら、その1画像を**スキップして次へ**。WORKLOGに「⚠️生成失敗・要再試行」と記録
3. ⚠️**同じ画像で無限に粘らない**。他のキャラ・他の背景に進んでよい(WORKLOGに未完了を残す)

⚠️Error連発で長時間止まるより、**進めるものを進める方が遥かに価値がある**。
運営者は「目が離せない」と困っている。粘って詰まると余計に悪化する。

### 0.48 ⚠️Codex: 確認を求める前に、この判断表を見よ(★最重要・2026-07-21 追記)

**運営者から明確な指摘があった**:
> 「Codex は細かい作業ごとに確認のために作業を止めてしまい、全然目が離せない」

⚠️**確認を求めるのは、本当に必要なときだけにする。** 大半のケースは自分で判断して進めてよい。
「怒られないように」で確認を挟むのは、逆に運営者の時間を奪って**信頼を失う行動**である。

#### 0.48.1 「確認を求めない」もの(⚠️自分で決めて進める)

| こういう場面 | 判断 |
|---|---|
| 実装の詳細(変数名・ヘルパ関数の分割単位・importの並び順) | ⚠️**自分で決める**。運営者に美的判断を求めない |
| SPEC/ICONS/EVENTS等に**書いてある通りに実装するだけ** | ⚠️**確認不要**。書いてあるのだから聞かず実装する |
| 仕様に無いが**一つの妥当解が明白**な小さな判断(例: エラーメッセージの文言、内部変数の初期値) | ⚠️**自分で決める**。WORKLOGの「判断ログ」に一行残せば十分 |
| 型エラー・lintエラーの機械的な修正 | ⚠️**そのまま直す**。方針変更を伴わない修正は聞かない |
| ファイルの分割・関数の抽出などのリファクタ | ⚠️**やる/やらないを自分で決める**。ただし本体側ファイルへの追記は §0 の制約に従う |
| §12.15 に従った画像生成の各枚 | ⚠️**プロンプトを組んで生成**。ペルソナ確認・画風確認は要らない(既に SPEC に書いてある) |
| 「XX と YY のどちらの表現が良いか」レベル | ⚠️**自分で決めて WORKLOG に残す**。運営者に美的判断を委ねない |

#### 0.48.2 「必ず確認を求める」もの(⚠️これだけは止まる)

| こういう場面 | 理由 |
|---|---|
| **本体側ファイル(SPEC §0の一覧)への追記** | パージ容易性を壊すため |
| **backend への変更** | ⚠️禁止事項。触る前に必ず確認 |
| **依存パッケージの新規追加**(`pnpm add ...`) | 運営者の環境と方針に関わる |
| **CONSTRAINTS §0 の INV-1〜4 / §4.1A の W-1〜6 に触れる** | 法務の不変条件を破りうる |
| **本文(STORY/SIDE/BIBLE)の書き換え** | ⚠️Codex は仕様書を読むだけ。書き換えない |
| **仕様書間の明白な矛盾を見つけた** | WORKLOG「仕様への申し送り」に書いて次の指示を待つ |
| **設計判断の変更**(方針レベル: 例「イベントに分岐を足す」「アイコンを画像に変える」) | 本書のどこかに書かれた方針を覆すもの |
| **同じ問題を3回以上試して解けない** | 空回りを止めるため。WORKLOG に状況を書いて止まる |

#### 0.48.3 判断に迷ったときの一問一答

**「これは確認すべきか?」と思ったら、次を順に見よ:**

1. **仕様書に書いてあるか?** → 書いてあるなら**聞かず実装**。書いてある内容を確認しない
2. **本体側ファイル・backend・依存追加・法務・本文・方針変更に触れるか?** → 該当すれば**聞く**
3. **どちらでも動く選択肢が2つ以上あるか?** → **より単純なほう**を選んで進む。WORKLOG に一行「Xを選んだ。理由: Yより単純だから」
4. **エラーが出て、原因が仕様の解釈でなく実装ミスか?** → **自分で直す**
5. **3回以上試して解けないか?** → **止まる**。WORKLOG に「未完了の作業」として書く

⚠️**この5ステップで「聞く」に至らないものは、聞かない**。

#### 0.48.4 「作業ログの粒度」も抑える

WORKLOG は**フェーズ単位・完了単位で更新**するのが基本。⚠️「関数1つ書いた」「テスト1つ通した」のたびに更新しない。
- OK: 「P1 完了。engine.ts + rng.ts + vitest 全通過」
- NG: 「引数の型を `number` から `Piece` にした」「テストを1つ追加した」「変数名を `n` から `count` にした」

**運営者への進捗報告も同じ**。区切りのいい単位で1回、簡潔に。⚠️実装の逐次実況を求められていない。

#### 0.48.5 ⚠️止まっていいのは「本当に判断が要るとき」だけ

上記の判断表を通しても「聞くべき」に該当するもの以外は、**自律的に進める**こと。
運営者は「作業してくれるのは良いが目が離せない」と言っている。
⚠️これは**自律性への信任**である。応えるのが仕事。

## 3. ゲーム仕様 — コア

### 3.1 盤面
- 8×8 マス。ピースは6種の花(§3.2)
- 操作: 隣接2マスのスワップのみ(ドラッグ or タップ2回)。マッチが成立しないスワップは**元に戻る**(戻りアニメあり、手数消費なし)
- 3個以上の直線一致で消去 → 上から落下補充 → 連鎖判定を繰り返す(カスケード)
- 手数制(タイムはなし)。手数消費はマッチ成立スワップ+ブースター使用のみ

### 3.2 ピース(6種固定)
6種は全ステージ共通(認識学習を壊さないため)。**色+形の両方で判別**(色覚多様性対応)。

| id | 花 | 色相 | 形の特徴 |
|---|---|---|---|
| matsu | 松 | 深緑 | 三角シルエット |
| ume | 梅 | 紅 | 丸5弁 |
| sakura | 桜 | 桃 | 切れ込み5弁 |
| ajisai | 紫陽花 | 青紫 | 4弁の塊 |
| himawari | 向日葵 | 黄 | 放射 |
| kiku | 菊 | 白(生成り) | 細弁の球 |

描画は**インラインSVG(プロシージャル)**。画像ファイルを使わない。
⚠️Codex: 特定の既存3マッチ作品(Candy Crush等)の配色・形状・盤面の見た目を参照・模倣しない。
(研究根拠: Tetris v. Xio 判決 — 個々の要素が許されても「累積的な look and feel の類似」で著作権+トレードドレス侵害になる。
ルール(スワップ/連鎖/手数制)自体はアイデアで自由だが、表現は完全独自に作ること。実装中に他作品のスクショを参照しない)

### 3.3 特殊ピース(ブースター)の生成
| 生成条件 | 生成物 | 効果 |
|---|---|---|
| 4個直線 | **短冊**(生成マスに) | 起爆でマッチ方向と**直交**する1列を薙ぎ消す(横4連→縦短冊) |
| L/T字5個 | **鞠** | 起爆で周囲3×3を消す |
| 5個直線 | **月** | 任意の隣接ピースとスワップで起爆: その色を盤面から全消し |

**組合せ起爆**(隣接スワップで両方を起爆した場合):
| 組合せ | 効果 |
|---|---|
| 短冊+短冊 | 十字(縦横1列ずつ) |
| 短冊+鞠 | 3列まとめて薙ぐ(方向は短冊に従う) |
| 鞠+鞠 | 5×5消去 |
| 月+短冊 | その色のピースを全て短冊に変えて順次起爆 |
| 月+鞠 | その色のピースを全て鞠に変えて順次起爆 |
| 月+月 | 全盤面消去 |

⚠️Codex: 組合せの**抽象ルール**はジャンル標準文法(法的に自由)。ただし名称・見た目・演出は本書の独自定義(短冊/鞠/月)を使い、他作品の用語(ストライプ/ラッピング等)をコード内でも使わないこと。

### 3.4 季節外れの花(本作のひねり。これ以外のひねりは追加しない)
- 盤面に**最大1輪**、「前月の花」が特別駒として出現する(通常マッチには使えない)
- 隣接マスでマッチを成立させると「散る」: **手数+1 を返し**、+500点
- 見た目: 通常ピースよりわずかに淡く、ゆっくり揺れている(§9.4)
- 出現率はステージ定義で制御(§5)

### 3.5 目標・スコア・星
- 目標タイプは v1 では**収集のみ**(「桜を24枚」等。指定花の消去数)。スコアは並走で加算
- スコア: 基礎 = 消去1個10点。連鎖倍率 ×1.0/×1.5/×2.0/×2.5…(連鎖数-1 ごとに+0.5)
- 星: ★1=目標達成(クリア) / ★2=スコア閾値A / ★3=スコア閾値B(閾値はステージ定義)
- 手数が尽きたら失敗。**失敗画面は責めない文体**(「また来てね」系。研究根拠: 羞恥で縛るUXはリテンションを毀損する)

### 3.55 道具(持ち込みアイテム) ※§3.3の盤面生成ブースターとは別物

### 3.57 待機時のひとこと(店主の独り言)

盤面下の一言枠に、**プレイヤーが手を止めている間だけ**若菜の独り言が流れる。
狙いは「一人で店番をしている時間の手触り」。**賑やかしではない**。

#### 表示ルール(静けさを壊さないこと)
- 無操作 **4秒**経過で表示。以後の最短間隔 **25秒**
- **1ステージ内で最大5回**まで。それ以上は黙る(沈黙も演出)
- 連鎖・落下・ブースター起爆・ボス行動の演出中は**絶対に出さない**(演出を邪魔しない)
- 表示は 6秒でフェードアウト。操作したら即座に消える
- 設定で「ひとことを表示しない」を選べる(§設定に項目追加)

#### データ構造(組み合わせ方式)
1万種類を個別に書くと質が落ちるため、**単独で完成した文を2つ繋ぐ**方式にする。
どの組み合わせでも文法・語調が破綻しない(＝連結を前提にした半端な文を書かない)。

```ts
type Bark = {
  id: string;
  text: string;              // 単独で完成した一文。これだけで成立すること
  tags: string[];            // 文脈タグ(下記)。空配列=いつでも可
  rarity?: 'common' | 'rare'; // rare は出現確率 1/100
};
type BarkData = { main: Bark[]; sub: Bark[] };  // 主文プール / 添え文プール
```
- 表示文 = `main` から1本 + **50%の確率で** `sub` を1本足して改行連結
- 目標規模: **主文 250本 / 添え文 45本** → 単純計算で 250 × 46 = **11,500通り**
  (タグ適合フィルタ後の実効も数千通りを確保する)
- ⚠️Codex: **文章の自動生成・テンプレート穴埋めをしない**。全文が人手で書かれたデータであること。
  足りない分をAIで水増しすると本作の文体規律(BIBLE §1)が壊れる

#### 文脈タグ(選択はタグ適合で行う)
| 種別 | タグ例 | 主文の目安 |
|---|---|---|
| 月 | `m1`〜`m12` | 各10本 = 120本 |
| 盤面状態 | `好調`(3連鎖以上を直近に達成) `停滞`(30秒マッチなし) `残り僅か`(手数3以下) `目標間近`(達成90%) | 各8本 = 32本 |
| 進行段階 | `序盤`(1-3月) `中盤`(4-8月) `終盤`(9-12月) | 各10本 = 30本 |
| 関係段階 | `関係1`(1-3月/客) `関係2`(4-7月/常連) `関係3`(8-11月/近い) `関係4`(12月以降/知っている) | 各8本 = 32本 |
| ボス戦 | `春荒` `五月雨` `野分` `大霜` | 各4本 = 16本 |
| 稀 | `rare` (1/100。祖母のこと、町のこと、ふとした本音) | 20本 |
- 添え文45本は短い一言(「……ふう」「手が冷える」「そういう日もある」等)で、タグは最小限にして汎用性を持たせる

#### 声の規律(BIBLE §1に従う)
- **若菜の声**。短い言い切り。感情語で説明しない。「!」は使わない
- 独り言なので敬語ではない(接客時の丁寧語とは別の声。ここが彼女の素)
- プレイヤーへの語りかけをしない(「がんばって」「すごい!」は禁止。**画面の外を見ない**)
- レンの話題は関係段階タグに従う。12月の種明かし前に核心へ触れない

#### 例(文体の基準。この密度で書く)
主文: 「水仙の水は、浅く。」`m1` / 「今日は、まだ誰も来ない。」`m1,停滞` /
「梅の根元は、詰まった音がいい。」`m2` / 「桜は、散り際まで売り物だ。」`m4` /
「雨の日は、白がよく出る。」`m6` / 「向日葵は、水を汚す。」`m7` /
「菊は、光の花。」`m10` / 「あの子、今月はまだ来ていない。」`関係2` /
「祖母なら、もっと早く手が動いた。」`rare`
添え文: 「……ふう。」/「手が冷える。」/「そういう日もある。」/「悪くない。」/「まだ夕方だ。」

### 3.6 詰み検出とシャッフル
毎手番後に「可能なマッチが存在するか」を全探索(8×8×2方向=112スワップ検査で十分軽い)。
なければ「風が吹いて…」の短い演出とともに自動シャッフル(手数消費なし、既存の特殊ピースは保持)。

⚠️Codex: **「自動シャッフル」と道具の「打ち水」(§3.55)は別物**。効果が似ているので必ず区別すること。

| | 自動シャッフル(本節) | 打ち水(§3.55の道具) |
|---|---|---|
| 発動 | 詰みを検出したとき**自動** | プレイヤーが**任意**に使用 |
| 手数 | **消費しない** | **1消費** |
| 在庫 | 概念なし(何度でも起きる) | 在庫から1減る(上限5) |
| 演出 | 「風が吹いて…」 | 打ち水の演出(§9) |

盤面を並べ替える**処理そのものは共通の関数**にしてよい(というより共通化すべき)。
違うのは**発動条件・手数・在庫**だけ。⚠️2つの別実装を書かないこと。
⚠️また、**打ち水を使った直後に詰みが発生した場合は自動シャッフルが走る**(手数は減らない)。
この二重発動を禁止しないこと(禁止すると詰みのまま進めなくなる)。

### 3.7 乱数と運の配置(重要)
(研究根拠: King の Candy Crush 公式ポストモーテム「Luck in the Right Places」— 運は排除するのでなく、
制作から除去し、レベルへ**調整された量だけ意図的に配置**する)

- 乱数は**シード付きPRNG(mulberry32)**で一元管理。`Math.random()` 直接使用禁止
  ⚠️Codex: これはデイリー盤面の全員同一性(§7)とテスト再現性の両方の生命線。乱数呼び出しは必ず注入された rng 経由
- 各ステージ定義に「運パラメータ」を持つ:
  - `colors`: 補充に使う色数(4〜6)。少ないほど偶然のマッチ・連鎖が起きやすい=運が助ける
  - `boardPreset`: 開始盤面の固定配置(nullなら乱数生成。乱数生成時も「開始時に可能マッチ3つ以上」を保証するまで再生成)
  - `outOfSeasonRate`: 季節外れの花の出現率(0〜0.3)

## 4. ボス「季節の障り」

ボスはキャラクターではなく**天候**。3/6/9/12月の最終ステージがボス戦になる。

### 4.1 共通ルール
- ボスHP = **季節ゲージ**(和風の目盛り)。0 にすれば勝利。手数が尽きたら失敗
- ダメージ: 通常消去1個=1。短冊/鞠/月による消去分=1個2。連鎖倍率は適用しない(単純に保つ)
- **テレグラフ必須**: ボスの行動は必ず1手前に対象マスを予告表示する
  (研究根拠: 攻略可能性を塞ぐ理不尽はゲームメカニクス側で処理しないと耐えがたい〔キャラクター原理論文〕。
  予告→対処の余地、が本作のボス設計の背骨。**予告なし行動を実装してはならない**)

### 4.2 ボス4体
| ボス | 月 | 行動周期 | 行動内容 | HP目安 |
|---|---|---|---|---|
| 春荒(はるあれ) | 3月 | 2手ごと | 予告した1列のピースを横に1マス流す(端は反対端へ) | 120 |
| 五月雨(さみだれ) | 6月 | 3手ごと | 予告した2マスに雨溜まり(そのピースはマッチ不可。隣接マッチ1回で除去) | 150 |
| 野分(のわき) | 9月 | 4手ごと | 予告した4マスのピースを相互に入れ替える | 180 |
| 大霜(おおしも) | 12月 | 3手ごと | 予告した2マスを凍結(スワップ不可。隣接マッチ1回で解凍) | 220 |

HP・周期は調整値(プレイテストで変更可)。雨溜まり/凍結は盤面の1/3を超えて存在しないよう上限を設ける。

### 4.3 ボス演出(§9 の数値に従う)
- 登場: 画面が墨がにじむように翳る→天候エフェクト開始(2秒以内)
- 天候の持続表現は transform/opacity のみ、**盤面の視認性を妨げない**(プレイ可能性>演出)
- ダメージ時: 天候エフェクトが一瞬怯む。ゲージが目盛り単位で減る
- 撃破: 90msヒットストップ→雲が引いて光→花吹雪→ゲージ「晴」(全体3秒以内)
- 敗北: 天候が静かに引くだけ。責めない

## 7. 進行データ(保存)

バックエンド変更なし。**アカウントレジストリ**(既存API `i/registry/*`)に保存する。
既存実績: `packages/frontend/src/utility/hatady-prefs.ts` が scope `['client','hatady']` で同期保存している。**同じパターンを踏襲**。

- scope: `['client', 'hanaawase']`
- key `progress`: `{ v: 1, stars: Record<stageId, 0|1|2|3>, vignettesSeen: string[], hintsSeen: string[], disclaimerSeen: boolean, disclaimerRev: number, choices: Record<string,'A'|'B'>, tools: { hasami: number; tenaoshi: number; uchimizu: number }, toolsUnlocked: string[], updatedAt: number }`
  - `hintsSeen` = 表示済みチュートリアル項目のid配列(§3.58)。⚠️**boolean ではない**
  - `disclaimerSeen` = 初回の注意書き(§3.59)を表示済みか。
    ⚠️`hintsSeen` を空にしても**これは戻さない**(チュートリアル再表示で注意書きを再表示しない)
  - `disclaimerRev` = 読んだ注意書きの**版**(既定 `0`)。⚠️`DISCLAIMER_REV` 未満なら**既読の人にも再表示**する(§3.59)。
    マージは**大きいほう**を採る
  - `v` / `updatedAt` は §7.5 で必須
  - ⚠️会話の読み返し(§9.75)は**保存しない**(セッション内のメモリのみ)
  - `tools` = 道具の在庫(各0〜5, §3.55)。`toolsUnlocked` = 解禁済み道具id
  - ⚠️Codex: 獲得判定は**冪等**にすること(同じステージを★3で再クリアしても重複付与しない。
    「そのステージで初めて★3を取った時のみ付与」= `stars[stageId]` が3未満から3に上がった瞬間に加算)
- key `daily`: `{ lastPlayed: 'YYYY-MM-DD', streak: number, best: number, freezes: number, freezeMonth: 'YYYY-MM', plays: number, longest: number }`
- key `settings`: `{ se: boolean, motion: 'normal'|'reduced', barks: boolean }`
  (`barks` = §3.57 待機時のひとことの表示可否。既定 true)
- 端末ローカルキャッシュ(miLocalStorage)を初回描画用に併用してもよいが、正はレジストリ

⚠️Codex: `miLocalStorage` のキーは `packages/frontend/src/local-storage.ts` の型付きユニオンに追加が必要。
追加せず `localStorage` を直接触るのは既存規約違反(ただしゲーム内一時状態のみなら registry だけで足りる)。

### 7.5 保存の堅牢性(⚠️データ消失は本作で最悪の不具合)

本作の進行は**一年ぶんの物語**であり、失われると取り返しがつかない。
レジストリは**サーバーAPI**なので、通信失敗・複数端末・スキーマ変更のすべてを想定すること。

#### 7.5.1 バージョンとマイグレーション
全キーの直下に `v: number` を必ず持たせる(現行 `v: 1`)。
```ts
type SaveV1 = { v: 1; stars: Record<string, 0|1|2|3>; /* ... */ };
```
- 読み込み時: `v` が**未来**(自分が知らない値)なら**書き込みを止めて読み取り専用**にし、
  「新しい版で保存されています」と表示する。⚠️**古い形式で上書きしてはならない**(別端末の進行を破壊する)
- `v` が**過去**ならマイグレーション関数を順に適用して現行版へ。`migrate_1_to_2` の形で1段ずつ書く
- `v` が**無い**(初期実装のデータ)場合は `v: 1` とみなす
- ⚠️Codex: スキーマ変更は §14 の「要相談」。勝手に形を変えず、必ず `v` を上げてマイグレーションを書く

#### 7.5.2 書き込み失敗(オフライン・API エラー)
`i/registry/set` は**失敗しうる**。失敗を握り潰すと player は気づかないまま進行を失う。
- 書き込みは **miLocalStorage への保存を先に**行い、そのあとレジストリへ送る(ローカル先行・サーバー追従)
- レジストリ書き込みが失敗したら:
  - **ゲームは止めない**(遊べる状態を維持する)
  - 未送信フラグを立て、次の書き込み機会・画面遷移・再オンライン時に**再送**する
  - 3回連続で失敗したら、画面の隅に控えめな警告を出す
    (文言例: 「記録を保存できていません。通信を確認してください」。⚠️モーダルで遊びを止めない)
- ⚠️Codex: `await` を付け忘れて fire-and-forget にしないこと。失敗を検知できなくなる

#### 7.5.3 書き込みの頻度(⚠️API を叩きすぎない)
1手ごとに保存すると本体サーバーに負荷をかける。**保存はステージ境界のみ**。
| 契機 | 保存するか |
|---|---|
| ステージクリア/失敗の確定時 | する |
| 設定の変更時 | する(デバウンス 1秒) |
| デイリーの結果確定時 | する |
| 選択肢の決定時 | する |
| **1手ごと・連鎖ごと** | **しない** |
- 同一フレームで複数の保存要求が出たらまとめて1回にする(キーごとに最後の値だけ送る)

#### 7.5.4 複数端末の競合
同じアカウントを2端末で同時に遊べてしまう。完全な解決はしないが、**破壊は防ぐ**。
- 保存時に `updatedAt: number`(epoch ms)を含める
- 書き込み直前に読み直し、**サーバー側の `updatedAt` が自分の読み込み時より新しければ**、
  上書きせずマージする。マージ規則:
  - `stars`: ステージごとに**大きいほう**を採用(進行は減らさない)
  - `vignettesSeen` / `toolsUnlocked`: **和集合**(どちらかで見たものは見たことにする)
  - `tools`(在庫): **大きいほう**
  - `daily.streak` / `best` / `longest`: **大きいほう**
  - `choices`: **サーバー側を優先**(物語の選択は後から変えない)
  - `settings`: **自分側を優先**(最後に触った端末の意図が正しい)
- ⚠️この規則は「進行が巻き戻らない」ことだけを保証する。厳密な整合は目指さない

#### 7.5.5 データ破損・リセット
- 読み込んだ JSON が壊れている/型が合わない場合、**握り潰して初期化しない**。
  壊れた生データを miLocalStorage に退避してから初期状態で起動し、設定画面に復旧の導線を出す
- 設定の「進行のリセット」(design `02-meta` にあり)は**二段階確認**の実装済み仕様に従う。
  ⚠️リセットは registry と miLocalStorage の**両方**を消すこと(片方だけ消すと復活して混乱する)

## 8. 効果音(Web Audio・プロシージャル)

⚠️**効果音**(消去・落下・起爆・撃破)は音声ファイルを同梱せず、Web Audio 生成で `hanaawase/sound.ts` に集約。
(⚠️**環境音**は §8.5 で方針変更し CC0 実音源を使う。効果音とは別扱い。混同しない)

```ts
// 消去音の基本形(コピペ可)。連鎖ごとに pitch を上げて使う
const ctx = new AudioContext();
export function pop(pitch = 880, vol = 0.3) {
  const o = ctx.createOscillator(), g = ctx.createGain();
  o.type = 'sine';
  o.frequency.setValueAtTime(pitch, ctx.currentTime);
  o.frequency.exponentialRampToValueAtTime(pitch * 1.5, ctx.currentTime + 0.08);
  g.gain.setValueAtTime(vol, ctx.currentTime);
  g.gain.exponentialRampToValueAtTime(0.001, ctx.currentTime + 0.15);
  o.connect(g).connect(ctx.destination);
  o.start(); o.stop(ctx.currentTime + 0.15);
}
// 連鎖: pop(880 * 1.122 ** chainIndex)  // 五音音階ステップ(約2半音)で駆け上がる
```

- SE一覧: スワップ(短いクリック) / 消去pop(連鎖でピッチ上昇) / 短冊(シャッ) / 鞠(ぽむっ) /
  月(澄んだ鐘) / 散り(風鈴一粒) / ボス行動(低い太鼓) / クリア(五音の上昇アルペジオ)
- ⚠️Codex: `AudioContext` はユーザー操作後でないと再生できないブラウザ制約がある。
  初回タップで `ctx.resume()` する初期化を入れること。設定 `se:false` で全ミュート
- BGMは v1 では**実装しない**(無音+SEで成立させる。将来課題)

### 8.5 音の方針(⚠️2026-07-22 確定。効果音=生成 / 環境音=CC0実音源のハイブリッド)

**結論: 楽曲BGMは作らない。効果音は生成(§8)。環境音は CC0 実音源を鳴らす。**

#### なぜ楽曲を入れないか
1. **トーン**: 本作は「一人で店番をしている時間の手触り」(§3.57)が主題。
   ループ楽曲が鳴っていると、静けさそのものである待機時間が成立しない
2. 効果音(§8)が既にプロシージャル生成で完結しており、**楽曲の追加依存を作る理由がない**

#### 効果音と環境音の切り分け(★取り違えない)
| | 実装 | 理由 |
|---|---|---|
| **効果音**(消去・落下・起爆・撃破, §8) | ⚠️**Web Audio 生成のまま** | 連鎖ごとにピッチを上げる/ヒットストップに同期する等の**動的制御**が要る。実音源(固定音)では §9.2 の連鎖エスカレーションが死ぬ |
| **環境音**(水・雨・風・霜・店のざわめき) | **CC0 実音源をループ再生** | 質感が命。ノイズ生成では「それらしい」止まり。動的制御が要らない(ループで足りる)ので実音源の欠点が出ない。本作の「店の手触り」に直結 |

⚠️§3.2 の「画像ファイルを使わない」方針は**画像に限る**。環境音の実音源同梱はこれと矛盾しない
(画像は `flowers.js` で手続き生成できるが、水音・雨音は生成では本物に届かないため)。

#### 環境音の調達(⚠️CC0 のみ。ライセンスを1ファイルずつ確認)
- **入手先**: 第一候補 **Kenney.nl**(ほぼ全て CC0)。不足分は **freesound.org の CC0 タグ** / **BigSoundBank** / **OpenGameArt の CC0**
- ⚠️**サイトのトップが「無料」でも素材ごとにライセンスが違う**(CC0/CC-BY/NC/editorial が混在)。
  **CC0 であることを1ファイルずつ確認**してから採用する。CC-BY 以降(表記義務/改変制限/非商用)は**使わない**
- CC0 は著作権放棄なので MIT/AGPL のどちらにも無条件で組み込める(§9.9 と矛盾しない)。
  ⚠️ただし CC0 条文注釈「作者の推薦を示唆しない」に従い、NOTICE で「この音が花常を推薦している」と読める書き方をしない

#### 実装(`hanaawase/ambience.ts`)
- 置き場所: `packages/frontend/assets/hanaawase/sound/`(⚠️`/client-assets/` で配信済み・追記不要)
- 形式: **OGG**(Vorbis)。⚠️**短いループ**(10〜20秒)を継ぎ目なく繰り返す。1ファイル **300KB 以内**を目安に圧縮
- ⚠️**同時に鳴らすのは1トラックまで**(場面に応じて切り替え、重ねない)。切り替えは 1〜2秒のクロスフェード

| 場面 | 環境音 | 補足 |
|---|---|---|
| 通常の盤面 | 店の空気(静かな室内トーン) | ⚠️ほぼ無音に近い薄さ |
| 六月・雨の月 / ボス「五月雨」 | 雨 | 屋根に当たる雨のループ |
| 九月・ボス「野分」 | 風 | 唸る風のループ |
| 十二月・ボス「大霜」 | **静けさ** | ⚠️**環境音を止める**。無音そのものを冷たさに使う(実音源でも「鳴らさない」が正解) |
| 物語画面 | 背景IDに追従(§9.7.55) | `front_*`=外の気配 / `shop_night`=より静か / `market`=遠いざわめき |

- 音量は効果音より**明確に下**。効果音を邪魔した時点で失敗
- 設定の「効果音」OFF で環境音も止める(⚠️トグルは増やさない)
- ⚠️Codex: **旋律・和音・リズムを持つ音源を選ばない。** 気づかれない音が正解。
  「寂しいから音楽的なものを足す」は本作では誤り(§14 の「不可」に準じる)
- ⚠️**環境音が調達できない/未配置でも本編は動くこと**(音が無ければ無音で進む。落とさない)

#### ライセンス台帳(⚠️必須)
採用した音源は **`assets/hanaawase/sound/CREDITS.md`** に1ファイルずつ記録する:
`ファイル名 / 出典URL / ライセンス(CC0確認済み) / 取得日 / 加工内容(トリム・ループ化等)`。
⚠️CC0 は表記義務がないが、**将来「本当にCC0か」を再検証できるように**出典を残す(§9.9 の権利健全性のため)。

## 9. 演出仕様(juice) — 数値で固定

(研究根拠: "Juice it or lose it" 系の実証 — ゲームロジックに触れず提示層だけで体感品質は大きく変わる。
以下の実装テクは Web 実装知見の検証済み事項)

### 9.1 ピース消去(1回の消去 約0.3秒)
1. 白フラッシュ(60ms, opacity)
2. スケールポップ(scale 1→1.15→0, 180ms, オーバーシュート)
3. 花びらパーティクル4〜6粒(散布、DOM div + CSS アニメ)
4. スコア数字が浮く(+10, translateY -20px + fade, 400ms)

### 9.2 連鎖エスカレーション
- 連鎖 n 回目: 演出スケール ×(1 + 0.1n)、SEピッチ上昇(§8)
- コンボ表示「二連」「三連」…(和語)。3連鎖以上で画面シェイク(±2px, 150ms)

### 9.3 ヒットストップ
- 鞠/月の起爆・組合せ起爆・ボス撃破の瞬間: **全アニメを60〜90ms停止**してから再開
- (研究根拠: 動き・速度・パーティクルが同一でも、停止時間の差だけで「重い一撃」と知覚される。実装は setTimeout ひとつ)

### 9.4 その他
- 落下着地: squash(scaleY 0.85 + scaleX 1.1, 90ms → 戻り)。
  ⚠️Codex: **単一 scale() は禁止**(風船が膨らむようにしか見えない)。scaleX と scaleY を逆相で動かし面積を保存する(検証済み知見)
- 季節外れの花: 常時ゆっくり揺れ(rotate ±3deg, 3s ループ)。散る時は花びら10粒+風鈴音
- 画面シェイク: CSSクラス付け外しで再発火させる場合、**`void el.offsetWidth` で同期リフローを挟む**こと。
  同フレーム内の remove/add はブラウザが合体させて2回目以降再生されない(検証済み知見)

### 9.5 実装方針
- すべて **transform / opacity のみ**(60fps要件)
- パーティクルは **DOM div + CSSアニメ**で開始(数十粒レベルでは canvas より安くコンポジタ任せにできる)。
  数百粒常時が必要になった場合のみ canvas 検討(検証済み知見)。
  ⚠️Codex: パーティクル1粒ごとに Vue のリアクティブ state を通さない(粒ごとの再レンダーで死ぬ)。
  生成は素の DOM 操作 or 一括 v-for + アニメ終了で親ごと破棄
- アニメ強度: 設定 `motion:'reduced'` と `prefers-reduced-motion` の**両方**で全演出を停止し最終状態表示。
  加えて本体設定(`prefer.s.animation`)も尊重する

### 9.6 再アニメ事故の防止
盤面の再描画・データ再取得で入場アニメが再発火しないこと。`:key` の設計に注意
(v-for の key が変わる=再mount=再アニメ。ピースの key は「ピース個体ID」であって座標ではない)。

### 9.7 立ち絵と背景の演出(物語画面)

| `fukure` ふくれ | face_3 むむっ | — | 左右に小刻みに震える(`translateX ±2px` 5往復)+わずかに前傾 | 420ms |
| `tere` 照れ | — | face_3 照れ | 半歩引く(`translateY +3px` `scale .99`)。**戻りをゆっくり**に | 600ms |
| `odoroki` 驚 | face_4 びっくり | face_4 びっくり | 跳ねて潰れる: `translateY -14px` →着地で `scaleX1.12/scaleY.88` →復元 | 380ms |
| `shonbori` しょんぼり | face_5 うるうる | — | ゆっくり沈む(`translateY +7px`)+前傾。**次の発話まで戻さない** | 700ms |
| `majime` 真顔 | — | face_5 集中 | **動かさない**(呼吸も止める)。0.2sだけ `brightness(.92)` | 200ms |
| `kirakira` きらきら | face_6 目が星 | — | 大きく1回弾む+金の粒4つが立ち絵の周囲に散る(§9.7.4) | 700ms |
| `komari` 困り笑い | — | face_6 眉ハの字 | ゆっくり左右に1往復傾く(`rotate ±2.5deg`・下端支点) | 800ms |

- easing は原則 `cubic-bezier(.34,1.56,.64,1)`。ただし `tere` `shonbori` `komari` は `ease-out`(跳ねると軽薄になる)
- `transform-origin: center bottom` を全モーション共通に(足元を床に接地させたまま動かす)
- ⚠️Codex: レンの**耳と尻尾は表情PNGに描き込まれている**(§12.7)。モーションで別々に動かすことはできない。
  「驚きで耳が立つ」は `face_4` の絵が担い、`odoroki` モーションは立ち絵全体を跳ねさせるだけ

#### 9.7.15 感情IDはどこから来るか(⚠️現時点で未整備。Codexは勝手に推測しないこと)
セリフ行のデータ型(`hanaawase/story.ts`):
```ts
type Line = {
  who: 'wakana' | 'ren' | null;   // null = 地の文・帳面
  text: string;
  emo?: EmotionId;                // 省略時は 'heisei'
  bg?: BgId;                      // 省略時は直前の背景を継続
};
```
**表情は本文Markdownに指定済み**(全693箇所)。セリフ行の直前に `【若菜④】` `【レン②】` の形式で入っている。
番号は各ファイル冒頭の凡例(§12.7 の表情6種)に対応する。
⚠️Codex: 分岐マーカー `【A】【B】【合流】` および可変行マーカー `{B-xx=A: }` `【問い高】` は
**表情とは別系統**。パーサで混同しないこと(`【若菜N】`/`【レンN】` のみが表情)。

**背景は `[場面]` 見出しに指定済み**(§9.7.55 の背景ID)。1つの `[場面]` は1つの背景に対応し、
場面内で背景が変わる場合のみ本文中に `[背景=xxx]` を単独行で置く。

- ⚠️Codex: **表情・背景タグの追加・変更・削除は禁止。** 本文の意味に基づいて人間が割り当て済みであり、
  Codexが「ここは驚きのはず」と推測して書き換えると、本作の抑制した演出設計(§2.2「説明しない」)が壊れる
- 実装は「**`emo` 省略= `heisei`、`bg` 省略=直前を継続**」で全行が再生できる形にすること
  (サブキャストのセリフ `> 八重「…」` には表情タグが無い=立ち絵なしのため。§9.7.6-6)

本文の `[場面]` 見出し行末に `[背景=xxx]` の形で指定済み。**タグは意味(場所)を表し、

#### 9.7.2 発話バウンド(感情モーションとは別に、毎行かかる)
1行送るたび、**話者の立ち絵だけ**に軽い上下(`translateY 0→-6px→0` / 260ms / overshoot)。
感情モーションがある行は、感情モーションが発話バウンドを**上書き**する(二重にかけない)。

**非話者の後退**(会話の主役を明示する):
```
話者     : filter:none;                  translateY(0);    z-index:2
非話者   : filter:brightness(.68) saturate(.85);  translateY(3px);  z-index:1
遷移     : 240ms ease(filter と transform のみ。opacity は触らない)
```

#### 9.7.3 立ち絵の入退場
| | 動き | duration |
|---|---|---|
| 登場 | `opacity 0→1` + `translateY 12px→0` + `translateX ±10px→0`(画面外向きから寄る) + `scale .98→1` | 320ms |
| 退場 | `opacity 1→0` + `translateY 0→8px` | 240ms |
- 左のキャラは `translateX -10px` から、右のキャラは `+10px` から寄ってくる

#### 9.7.4 きらきらの粒(`kirakira` 専用)
DOMの `div` 4つ。立ち絵の上半身あたりからランダム方向へ `translate`+`rotate`+`scale 1→.4`、
`opacity 1→0`、700ms、粒ごとに ±60ms のディレイ。色は `--accent`。
⚠️粒は**4つまで**(§9.5 の DOMパーティクル上限方針。ここで盛ると一気に安っぽくなる)

#### 9.7.5 背景の切り替え
背景は §12.2 の6枚(`shop_day` `shop_evening` `front_spring/summer/autumn/winter`)。

| 状況 | 演出 | duration |
|---|---|---|
| **同じ場所の時間変化**(`shop_day`→`shop_evening`) | 単純クロスフェード。立ち絵はそのまま | 600ms ease |
| **場所が変わる**(`shop_*`→`front_*`) | 墨のにじみ暗転を挟む: 暗転in 280ms → 保持 120ms → 暗転out 380ms。**立ち絵も一緒に消して出し直す** | 計 780ms |
| **章が変わる** | 「月替わりの間」(handoff `02-meta` の `interlude`)を挟むので、背景遷移は不要 |

- 「墨のにじみ」= 墨色 `#2b2620` のレイヤーを `opacity 0→1` させつつ `scale 1.06→1`。
  単純な黒フェードにしない(和のトーンを保つため、わずかに拡大しながら閉じる)
- **常時のごく緩い Ken Burns**: `scale 1→1.03` を 20s `linear` `alternate` 無限。
  ⚠️**3%を超えないこと**。背景が動きすぎると本文から視線が逃げる
- 背景の選択は本文の場面設定から決める(§12.2 の背景タグ規約)。迷ったら `shop_day`

#### 9.7.6 ⚠️Codex: この節の実装上の落とし穴
1. **感情IDの分岐は `data-emo` 属性で書く。** `$style[emo]` や `{ [$style[emo]]: true }` は
   §0.4-1 のとおり**クラスが付かない**(エラーも出ない)。
   `<img :data-emo="emo">` + グローバル `<style>` の `[data-emo="odoroki"] { animation: ... }` で書くこと
2. **同じ感情が2行続くとアニメが再生されない。** CSSアニメは値が変わらないと再発火しない。
   `void el.offsetWidth` で同期リフローを挟んでから `animation` を付け直す(§9.5 と同じ手法)
3. **背景レイヤーと立ち絵を親子にしない。** 背景に Ken Burns の `transform` がかかるため、
   子孫の `position: fixed`(選択肢のツールチップ等)の基準が壊れる(§0.4-4)。
   背景と立ち絵は**兄弟**として同じコンテナに並べ、`z-index` で重ねること
4. **「動きOFF」/`prefers-reduced-motion` 時**: 感情モーション・発話バウンド・呼吸・Ken Burns を全停止し、
   表情PNGの差し替えだけ行う。背景切り替えはクロスフェードなしの**即時差し替え**(暗転も省く)。
   非話者の `brightness` による後退は**残す**(演出ではなく可読性のための情報表示なので)
5. **PNG未支給時**(§12.3 プレースホルダ): モーションは**そのまま動かす**。
   プレースホルダの矩形が跳ねるだけでもタイミング調整はできるので、絵の到着を待たないこと
6. **サブキャストには立ち絵がない。** 八重・玄・辰巳・犬飼らのセリフは本文で `> 八重「…」` の
   引用形式で書かれており、**表情タグが付かない**。この行では立ち絵を動かさず、
   簡易シルエット(§12.3)+名前表示のみ。⚠️若菜・レンの立ち絵を代わりに喋らせないこと

### 9.75 会話の読み返し(バックログ)

物語中に**読み飛ばした/読み返したい行**へ戻れる機能。⚠️UI上の名称は「**読み返し**」。
「バックログ」「履歴」の語は使わない(§2.4 の漢語基調)。

#### 開き方
| 入力 | 動作 |
|---|---|
| 会話枠の右上の小さな導線(`ti-list`) | 開く |
| ホイール上スクロール / 上フリック | 開く(⚠️VNの慣習。実装必須) |
| `PageUp` / `↑` 長押し | 開く |
| `Esc` / 下スクロールで最下部 | 閉じる |

#### 中身
- 話者名 + 本文を**時系列で縦に**並べる。⚠️**帳面の頁**の意匠にする(チャットの吹き出しにしない)
- 収録するもの: **会話・地の文・帳面(日記)・選択肢で選んだ結果**
- 話者の色分けは名前の色のみ(若菜=`--accent` / レン=`--ai` / サブキャスト=`--sub` / 地の文=名前なし)
- ⚠️**立ち絵・表情は表示しない**(読み物として読ませる。画像を並べると重い)
- 最下部が現在地。開いた瞬間は**最下部から始まる**

#### ⚠️Codex: 設計上の判断(理由つき)
1. **行き先へ飛べない(読むだけ)。** 過去の行をタップしてもそこへ戻らない。
   ⚠️分岐(§2.4)と進行状態の整合が壊れるため。⚠️「ここから再生」を実装しない
2. **保持は現在の場面(ビネット)単位ではなく、直近 `200行`。** 場面をまたいで遡れる。
   200行を超えたら古いものから捨てる(メモリ保護)
3. **章をまたいだ読み返しは花手帖の「通し読み」が担う**(§2.4)。読み返しと役割を分ける。
   ⚠️読み返しに「最初から読む」導線を置かない(通し読みと機能が重複する)
4. **周回中(§イベント)も有効。** ⚠️ただしパズル中には出さない(盤面の上に被せない)
5. 待機時のひとこと(§3.57)は**収録しない**。⚠️独り言であって会話ではないため
6. 保存しない(セッション内のメモリのみ)。⚠️registry に書かない(§7.5.3 の書き込み頻度方針)

#### アクセシビリティ
- `role="log"`、各行は読み上げ可能なテキスト
- キーボードだけで開閉・スクロールできること(§13.5.2)
- 「動きOFF」時は開閉のアニメーションを省き即座に表示

### 11.5 games.vue への追加

### 12.15 ⚠️Codex: 画像生成の実務ルール(★生成前に必ず読む)

#### 1. 寸法は**アスペクト比**で指示する。ピクセル値で指示しない
画像生成モデルは「1920×1080で生成して」と書いても**その解像度では生成しない**。
近い比率で生成してから後処理でリサイズするため、**ピクセル単位の厳密な制御は期待できない**。
- ⚠️プロンプトには **`16:9`** `1:1` `9:16` のように**比で書く**。比の指定は比較的安定して反映される
- 本書の各所にある `1920×1080` 等の数値は**保存時の目安**であって、生成プロンプトに書く値ではない
- 必要な最終寸法にするのは**生成後のリサイズ**で行う

| 用途 | 生成時に指示する比 | 保存時の目安 |
|---|---|---|
| 背景(§12.75) | **16:9** | 1920×1080 |
| 立ち絵 | **2:3**(縦長) | 幅800前後・透過PNG |
| 表情差分 | **1:1** | 512×512・透過PNG |
| ロゴ | ⚠️生成しない(SVG/CSSで組む。§12.0-7) | — |

#### 2. 利用枠の消費が速い(★§0.5.1 の優先順位が効く理由)
画像生成は**テキスト作業の3〜5倍の速さで利用枠を消費する**。
- ⚠️**候補を10枚並列生成するような使い方をしない。** 1枚ずつ、確認しながら進める
- ⚠️**1枚生成するごとに `HANATSUNE-WORKLOG.md` の進捗表を更新する**(§0.5.1)。
  枠が尽きた時点で「どこまで作ったか」が残るように
- 生成は1枚あたり**30秒〜2分**かかる。混雑で変動する

#### 3. 参照画像の渡し方
- `-i` フラグでローカル画像を参照素材として渡せる。**複数枚は `-i` を繰り返す**
- ⚠️**プロンプト本文で各画像の役割を明示する**(例:「1枚目のキャラクター造形、2枚目の画風」)。
  役割を書かないと意図とズレる
- 参照シートの場所: `packages/frontend/hanaawase/ref/`
  (`wakana.png` / `ren.png` / `kiyoba.webp`)

#### 4. 後始末
生成の副産物が `~/.codex/generated_images/` に溜まる(数百MB規模になりうる)。
⚠️作業の区切りで整理すること。**リポジトリに混入させない**。

### 12.75 背景の画像生成ルール(★全背景に適用。§12.7 のキャラルールとは別)

ここを外すと、綺麗なのに使えない絵ができる。

#### 12.75.1 画風(既存の意匠と揃える)
- **色数を抑えた絵本調**。キャラ(§12.7)ほど強くデフォルメせず、**線は細く、面で描く**
- パレットは既存の基調に寄せる: 墨 `#2b2620` / 生成り `#f4efe3` / 朱 `#c4383d` / 藍 `#2d4a73` /

- 質感はフラット〜わずかなグラデーション。⚠️写真的なレンダリング・強い光芒・レンズフレアを使わない
- 昭和の商店街の空気。⚠️観光ポスターにしない

#### 12.75.2 ⚠️構図(最重要。ここが本節の核心)
背景の上には**必ず文字と立ち絵が乗る**。したがって:

| 領域 | 扱い |
|---|---|
| **中央下 40%** | ⚠️**情報が乗る。主題を置かない。** 暗く・平坦にする(会話枠/カード/ボタンが来る) |
| **左右の下端** | ⚠️立ち絵が立つ(PC 170×400 / モバイル 120×300)。**細かい描き込みを置かない** |
| **上部 30%** | ここに主題を置く(空・軒・提灯・遠景) |
| 中央上 | イベントホームではロゴが乗る。⚠️**強い模様を置かない** |

- ⚠️**画面全体の明度を落として描く。** UI側でさらに暗くするのではなく、**最初から背景として引っ込んだ絵**にする
- **消失点・視線誘導を中央に集めない**(中央は文字が来る)
- ⚠️人物を描かない(立ち絵と競合する)。**人影・シルエットなら可**

#### 12.75.3 形式
- ⚠️**生成時は「16:9」と比で指示する**(§12.15-1。ピクセル指定は守られない)。保存時の目安 1920×1080 の PNG
- 置き場所: 本編は `assets/hanaawase/bg/`、イベントは `assets/hanaawase/events/<id>/img/`
- ⚠️1枚あたり **400KB以内**を目安に(モバイル配慮)。必要なら減色する

## 13.5 入力とアクセシビリティ(未定義だった領域)

### 13.5.1 操作の受け付け
盤面の操作は **タップ2回** と **ドラッグ** の**両方**を必ず実装する(§3.1)。
| 入力 | 挙動 |
|---|---|
| 1回目のタップ/クリック | 選択(design `01-core` の金色リング) |
| 2回目・隣接マス | スワップ実行 |
| 2回目・非隣接マス | **選択の移動**(エラーにしない) |
| 2回目・同じマス | 選択解除 |
| ドラッグ(8px以上) | 離した方向の隣接マスとスワップ |
| ドラッグ(8px未満) | タップとして扱う |
- ⚠️`touchstart` で `preventDefault` しすぎない。**ページのスクロールを殺さない**こと
  (盤面の上でだけ抑止する。ダブルタップズームは盤面上で抑止してよい)
- 演出中(`busy`)の入力は**捨てずに1手だけ先読みキューに入れる**。
  上級者は演出を待たずに次を打つ。捨てると「入力が抜けた」と感じる

### 13.5.2 キーボード操作(全画面で必須)
本体が Web アプリである以上、キーボードだけで完結できること。
| キー | 盤面での動作 |
|---|---|
| 矢印 / `hjkl` | カーソル移動 |
| `Space` / `Enter` | 選択・スワップ実行 |
| `Esc` | 選択解除 → もう一度でポーズ |
| `1` `2` `3` | 道具(鋏/手直し/打ち水) |
- カーソルには**選択リングとは別の可視フォーカス枠**を出す(キーボード使用時のみ)
- モーダル(開始前/ポーズ/リザルト)は**フォーカストラップ**を実装し、`Esc` で閉じる
- ⚠️`outline: none` を安易に書かない。§0.4 とは別の事故として頻出

### 13.5.3 スクリーンリーダー・色覚
- 盤面は `role="grid"`、各マスは `role="gridcell"` + `aria-label="桜 3行5列"`(花名を読む)
- 手数・目標・スコアの変化は `aria-live="polite"` の領域で通知する。
  ⚠️連鎖のたびに読み上げると洪水になるので、**通知は手番の確定時のみ**
- 一言枠(§3.57)は `aria-live="off"`。**独り言は読み上げない**(操作に必要な情報ではない)
- 色覚: 6種は**色+形の両方で判別**済み(§3.2)。⚠️これを崩す変更を加えない。
  白黒に変換して6種を区別できるかは、ピースSVGを変えたら毎回確認すること

### 13.5.4 パフォーマンス予算(60fps を守るための上限)
| 項目 | 上限 |
|---|---|
| 同時に存在する DOM パーティクル | **60個**(§9.5) |
| 1回の消去で撒く花びら | 1ピースあたり **4〜6粒** |
| 盤面の DOM 要素 | 64マス + パーティクル。**マスを毎フレーム作り直さない**(keyed で使い回す) |
| アニメーションに使うCSSプロパティ | **`transform` と `opacity` のみ**(§14) |
| 1フレームの JS 実行 | 8ms 以内。連鎖判定は同期で回してよい(8×8は十分軽い) |
- ⚠️`filter: blur()` を演出に使わない(モバイルで落ちる)。翳りは**半透明レイヤーの重ね**で作る
- モバイル実機(できれば数世代前の端末)で **P3 完了時に一度必ず確認**する。
  最後にまとめて確認すると、juice の作り直しになって手戻りが大きい
